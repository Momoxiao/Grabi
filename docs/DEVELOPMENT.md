# Grabi

**一个快捷键搞定的 macOS 截图工具。** 原生 Swift + 纯 AppKit，菜单栏常驻，不依赖 SwiftUI、不联网、不带 Electron。

**A one-shortcut screenshot tool for macOS.** Native Swift + AppKit, lives in the menu bar, no SwiftUI, no network, no Electron.

---

## 截图交互：一个键，三种截法

按一次快捷键进入截图模式，**不需要事先选模式**——候选框跟着鼠标走：

| 你的操作 | 会发生什么 |
|---|---|
| 移动鼠标到某个窗口上 | 实时高亮该窗口的边框，标签显示窗口名和像素尺寸 |
| 移动到桌面 / 窗口之间的空隙 | 候选框变成整块屏幕 |
| 在候选状态下单击 | 截取当前候选（窗口或全屏） |
| 按住并拖动 | 变成自由框选，实时显示尺寸（松手后、拖走前可在预览边缘拖手柄调节） |
| 按住 ⇧ 拖动 | 锁成正方形（边长取位移更大的那条轴） |
| 按住 ⌥ 拖动 | 以按下点为中心向外扩 |
| 按空格 | 强制切到整屏候选 |
| 按 ⏎ | 采用当前候选 —— 和单击走同一条判断，不用去碰鼠标 |
| 按 Esc | 取消 |

还没有候选时 ⏎ 不接，原样交回系统——接住却不做事，等于那个键凭空消失了。

> 这一轨以前还有三条：方向键平移、`⇧ + 方向` 改大小、`⌥ + 方向` 一步 10 像素。
> 已删除，原因见文末「方向键"按了没反应"」一节：
> 调好的那一格会被下一次鼠标移动吞掉，而鼠标几乎一定在动。要精确框选就按住拖动
> （`⇧` 锁正方形、`⌥` 从中心），那两条在松手前不会失效。

进入截图模式时，鼠标所在的那块屏顶部会浮一条操作提示，**持续显示**到
你第一次按下鼠标、或 5 秒后自动收起（早期版本画一帧就没了，等于没提示）。
它只说三段：怎么选、怎么定、怎么退。`⇧ 正方形` / `⌥ 从中心` 这一组
**在你真的开始拖动之后**才出现，画在选区角标的第三行上——顶部那条一收，
手上正在用的键正好出现在眼睛正在看的地方。

判断"单击"还是"框选"的规则很简单：松手时位移小于 5pt 就当单击。所以同一按键既能选窗口、又能画区域，不用切模式。

多显示器下每个屏幕都会铺一层，拖拽会收敛在起始屏幕内（暂不支持跨屏拼接）。

## 截图完成后：就地预览

不会在屏幕角落弹卡片，而是**直接在你刚框选的位置**浮出预览面板——边框和位置
正好等于那块地方，**选区之外压暗**，观感和截图过程完全一致。面板自带投影，
从背景里浮起来。工具栏浮在面板旁边（下方放不下就移到上方，两侧都不够就贴进
面板内侧底边）。

未拖走时，预览边缘会显示八个调节手柄；拖动它们会回到“重新框选”模式，按新范围重截。

**预览面板可以拖动**：在图上按住空白处拖走即可（文字块所在的位置留给选字，
不会误拖）。**一旦拖动，周围压暗会自动淡出**——既然你已经要把它挪开看别处了，
继续压暗只会碍事。

预览一旦拖走就会固定：此时边框手柄停用，不会再用拉框改变窗口尺寸；
调整观看大小只使用滚轮，避免显示尺寸和截图内容脱节产生黑边。

工具栏（从左到右）：

| 按钮 | 作用 |
|---|---|
| 画笔 | 点一下进入画笔，**直接在图上按住拖就能圈**；再点一下（或 `Esc`）收起 |
| 矩形 / 椭圆 / 箭头 / 直线 | 四种形状**各一颗按钮，点哪颗就是哪颗**。第一下是选中，不是"换到下一种" |
| 色块 | 图标就是当下那个颜色。点开是**六档候选色 + 三档线宽 + 系统调色盘**，一次点开设完 |
| 撤销 | 撤掉最近一笔；**刚清空过的话，按它把整批还回来**。没有可撤的东西时是灰的，不是"按下去叮一声" |
| 清空 | 撤掉这张图上所有标注（一笔一笔撤到第十笔不是"撤销"，是体力活）。图上没东西时是灰的 |
| 识别文字 | 主按钮，识别后在原位画出可点选的高亮框 |
| 复制图片 | 把这张图放进剪贴板，右下角浮一条带尺寸的回执；**预览保持打开**，可以直接去目标 app 粘贴，也可以继续选字或标注。截图本身不会自动进剪贴板。已经保存过的那张会**连文件 URL 一起**写进剪贴板，粘到访达 / 聊天工具里得到的是文件本身 |
| 保存 | 存成文件（磁盘那一份）。保存成功后**关闭预览**，并给一条「已保存」提示。保存成功过的那张不会再提供重复保存按钮，避免同一秒写出第二个同名文件 |
| 丢弃 / 移到废纸篓 | 没保存过（按钮写「丢弃」）：关掉面板，不写文件，剪贴板也不动。已经保存过（按钮和 tooltip 都换成「移到废纸篓」）：把那份文件**移到废纸篓**（连同名 `.txt`），可以找回；移不进去（只读挂载点、外置盘、网络盘）时**面板不关**，弹框说清原因和文件还在哪儿，默认按钮是「在访达中显示」 |

OCR 模式下工具栏换成文字那一排：**复制文字**（只复制划选中的；没划选会提示先划一段）/
**复制全部文字** / **复制图片** / **回到图片**。识别完在图上按住拖过几行选中，
或者直接对着某一块字**右键** —— 菜单里就有「复制文字」，成功后面板保持打开、字就在剪贴板里了，
右下角同时给你一条「已复制 N 个字符」的回执。工具栏和右键走的是同一个动作，
不会出现"按钮说复制文字、右键说复制全部"这种两套说法。键盘 `⌘C` 仍保留
“没划选就直接复制全部”的顺手路径，工具栏那颗按钮则不会替你猜。

选中哪颗工具，那颗就**亮起一块常亮的底**（不是把图标放大一档 —— 那颗会改整排的宽度，
刚点完旁边几颗就从鼠标底下溜走了）。画笔时鼠标换成**一枚笔尖环**，环心就是落笔点；
形状时是十字。按住 `⇧` 拖：矩形 / 椭圆锁成正的，箭头 / 直线锁到 45° 的整数倍。

画着的时候按 `Esc` 或点面板外：**先停笔**，面板还在；再按一次才收走。
一笔圈到一半就被收走，等于替用户决定"这一下不算"。

标注画在**屏幕上的那一笔，就是存进文件的那一笔**：坐标按选区归一化（0…1），
线宽按屏算成 3pt（可改细 / 中 / 粗），落盘时按图片像素尺度重算一遍倍率 —— 1440×900
的屏截出来的一张图，屏上 3pt 在文件里正好 6px。这一条链在 `--logic-selftest` 里对着量
（「标注」那一组），因为它是"看着对、存出去糊了"最容易翻车的地方。

「保存 / 丢弃」那两句悬停说明是**按状态现取的**，不是同一句话挂两处：已经保存过时，
按钮改成「移到废纸篓」，删的是磁盘上那一份；没保存过时只关面板，不去碰剪贴板。
两句话写成一句就有一半是假的。

键盘和右键都在：

| 键 | 作用 |
|---|---|
| 回车 | 保存（写出文件并关闭预览） |
| Esc / ⌘W | 收走面板，不写盘，剪贴板也一个字节都不动 |
| 点图片以外的任意处 | **还没拖走 / 缩放过时**收走面板（刚截完那一瞬最顺手的出口）。一旦拖走或滚轮缩放过，这张就固定在屏幕上了，点别处不再收走 |
| ⌘C | 复制图片；OCR 模式下复制划选的文字（没划选则复制全部），复制后预览保持打开 |
| 右键图片 | 没保存过：复制图片 / 保存 / 丢弃。保存之后**只剩两条**：复制图片 / 在访达中显示（那份文件已经在磁盘上了，「保存」和「复制路径」都没意义）。OCR 模式下多两条：**复制文字 / 复制全部文字**，右键落在哪个字块上，就复制哪一处；**落在已经选中的文字上时保留整段选区**，不会缩成一个字 |
| hover 到图上 | 右上角浮出「×」，点它收走面板（不保存、剪贴板不动）；移开鼠标就收起来，不会长期占着角落 |

**默认既不落盘、也不进剪贴板**：截图只是把这张图摆到你眼前，进剪贴板要你按「复制图片」，
变成文件要你按「保存」。复制成功后面板保持打开，适合“截完继续选字或去别处粘贴”；
**保存成功**后面板关闭，右下角才给那条带文件名的**已保存**提示，点它可以在访达里定位；
复制、`Esc`、点面板外、换下一张都**不会**报「已保存」（那时图可能压根没落盘）。
它不会自己超时消失，也不会替你按「丢弃」。

把预览**拖到别处**（或滚轮缩放一次）之后，这张就"钉"在屏幕上了：点其它任何地方都不会
把它收走，它始终盖在最上层；这时仍然可以继续拖动移动位置，或滚轮调整显示大小。
收它只有三条路 —— 角落那颗「×」、`Esc` / `⌘W`、或者工具栏上的「丢弃 / 移到废纸篓」。
拖走之后工具栏会收起，操作入口换成图上右键和那颗「×」。

滚轮调整**观看倍率**只在拖走之后才生效（刚截完就滚不会误改大小），只改变显示大小、
不会改变截图内容或保存像素；进入“钉住”状态时会提示这一点。钉住后不能再用边框手柄改尺寸，
这是为了避免窗口 frame 和图片内容比例脱节后露出黑边。

## OCR：点选文字块

点「识别文字」后，识别到的每一行都会在**它原本的位置**画一个高亮框：

- 框是可以点的——点一下选中，按住拖过多行可以一次选一片
- 工具栏「复制」取走选中的文字，「全部」取走整张图的文字
- 框只覆盖文字块，**空白处的事件会穿透**，所以「点空白拖着挪面板」和
  「点文字块选字」互不打架
- 「回到图片」清掉高亮框，恢复成普通预览

框的视觉很克制：每一行只铺一层极淡的强调色底（提示"这里能选"），选中后按行
合成**一条连续色带**——用琥珀色而不是系统蓝，不加圆角、不描边，观感仍像文本选区，
但不会和 macOS 自己的文字选中高亮混在一起。**原图上的字始终是主角**，叠加层不抢戏。

识别走系统 Vision 框架，**全程离线，图片不出本机**。

### 为什么最后选了"点选文字块"

前后试错三种方案，记下来免得再走回头路：

| 方案 | 结果 |
|---|---|
| 每行一个 `NSTextView` + 隐形文字层 | ❌ **结构就错了**。选择被切成几十个互不相干的视图，跨行拖选必然断裂、拖过头会跳行 |
| VisionKit 的 Live Text（`ImageAnalysisOverlayView`） | ❌ 理论上最优雅（苹果相册同款），但**运行时不可靠**：同一份代码时而返回空结果、时而直接挂住不返回；命令行环境下必然超时。它需要完整的 GUI 上下文，我无法稳定复现和验证 |
| **自绘高亮块 + 点选** | ✅ 参考 Capso 的 Visual OCR。行为完全可控，而且**用户看得见哪里能选，不需要盲拖** |

两个中途踩的坑（方案换了，但如果有人要自己实现文字层，仍然成立）：

1. 隐去文字层**不能**用 `alphaValue = 0`——那会把选中高亮一起隐藏，
   表现是"拖了半天什么都看不见，但复制出来又有字"。
2. 选中形状要改圆角，**只能走 `NSLayoutManager`**：重写
   `fillBackgroundRectArray(_:count:forCharacterRange:color:)`。
   `selectedTextAttributes` 管得到颜色，管不到形状。

**教训**：官方 API 不一定就是能用的 API。Live Text 看着正统，实际在非 GUI 上下文里
不可靠。最后回到自绘这条"笨"路，但把交互简化成"点块"之后，
反而比精确拖选更好用——也更容错。

## 安装

### 从源码构建

需要 macOS 14+ 与 Xcode 命令行工具。

```bash
git clone <repo-url> && cd Grabi
./build.sh release install
```

`install` 会把 app 同步到你**已有的安装位置**（`/Applications` 或 `~/Applications`，
优先跟随已存在的那一份，两者都不存在时用 `~/Applications`，并且会清掉另一处的副本
以免"打开的是旧版本"）。**这一步别省**：后台自启动带一条系统约束，只认标准应用目录，
放在项目目录里能手动打开，但系统不会自动拉起它。

### 打包分发

```bash
./package.sh     # 产出 dist/Grabi-<版本>.dmg 和 .zip
```

ZIP 用 `ditto` 而不是 `zip` 打包——后者会破坏 app bundle 的签名与扩展属性。

## 权限：关于「明明授权了，还一直要权限」

如果你自己改代码重新编译，可能会遇到这个。根子在**代码签名**。

macOS 的屏幕录制授权记录是绑定签名的。`codesign -s -`（ad-hoc 签名）的 designated requirement 里**包含 cdhash**，也就是二进制内容的哈希：

```
designated => identifier "com.grabi" and cdhash H"2f826904..."
```

结论是：**每重新编译一次，系统就把它当成一个全新的 app**，之前授的权全部作废。

换成开发者证书后，requirement 变成只认证书身份，不含 cdhash：

```
designated => identifier "com.grabi" and anchor apple generic
  and certificate leaf[subject.CN] = "Apple Development: ..."
```

**重新编译不会再让授权失效。**

`build.sh` 会自动优先使用本机已有的 Apple Development / Developer ID 证书，找不到才退回 ad-hoc。签名身份变化时还会自动清一次旧的授权记录，避免"系统设置里显示已勾选但实际无效"。

如果权限确实卡住了：

```bash
tccutil reset ScreenCapture com.momoxiao.grabi
```

或者用菜单栏里的「重置权限记录」。

### 检查真实权限状态

从终端跑 `--diagnose` 时，进程的 responsible process 是终端，权限判定会**继承终端的授权**，不代表以 `.app` 启动时的状态。所以 Grabi 会记录 GUI 启动时的真实状态：

```
屏幕录制权限    : 已授权 ✓
上次 GUI 启动    : 10-04 13:34:38　权限=无 ✗     ← 这一行才是真的
```

## 快捷键

| 操作 | 默认键 |
|---|---|
| 截图（窗口 / 区域 / 全屏） | `⌃⌥A` |

在「设置 › 快捷键」里点方框即可改键。冲突检测分三档：撞了 Grabi 自己的另一条
→ 直接不收；撞 macOS 自带截图那四条（`⇧⌘3 / 4 / 5 / 6`）→ 先问一句，坚持要用就给他；
只有一个修饰键（`⌘C`、`⌃A`、`⌥3`）→ 不收，理由写在框里。最后一档的原因见下面
「快捷键录制」那一节。

面板内的键（这一张表是从各视图的 `keyDown` / `keyEquivalent` 里逐条核出来的，
不是照记忆写的 —— 手写的 `--help` 就把 ⌃⌥S 抄成了 ⌃S）：

| 出现时机 | 键 |
|---|---|
| 选区覆盖层 | `Esc` / `⌘W` 取消　`空格` 切到整屏　`⏎` 采用候选　拖动中 `⇧` 正方形、`⌥` 从中心 |
| 截图预览条 | `回车` 保存（写出文件并关闭预览）　`Esc` / `⌘W` / 点面板外 **先停笔**（正画着的话），再按一次才收走面板（不写文件、不动剪贴板）　`⌘C` 复制（文字层有划选复制划选、否则全部；无文字层复制整图；**复制成功后预览保持打开**）　`⇧⌘P` 画笔　`⇧⌘S` 上一颗用过的形状　`⌘Z` 撤一笔（刚清空过 = 还回整批）　按住 `⇧` 拖 = 锁正方形 / 锁 45°　滚轮 = 调整观看倍率 |
| 主菜单（app 激活时） | `截图` —— 组合键跟着设置走，每次弹出重标 |
| 设置窗口 | `⌘1…⌘4` 切面板　`Esc` / `⌘W` 关闭 |
| 快捷键录入框 | 直接按新组合键（至少两个修饰键）　`Esc` 取消　`Delete` 清空 |

设置窗的 `⌘1…⌘4` 是 macOS 偏好设置窗的惯例（`NSTabView` 版自带）。这里为了观感
把标签页换成了顶部的分段控件，代价就是这套键得自己接：不接的话，在面板间来回跳
必须把一只手抬离键盘去点顶上那一排 —— 而改设置时最常做的恰恰就是这个动作。

接的位置是 `SettingsWindow.sendEvent` 重写，不是注册全局按键监视器：监视器挂在
进程上，忘了在关窗时摘就每开一次漏一个，而重写 `sendEvent` 天生只作用于这个窗口。
三个"不越权"的边界都进了断言：只认裸 `⌘`（`⌥1`、`⌃⌘1` 让给系统）、录制框正收键时
让路（`⌘1` 是完全合法的截图热键，抢了它就是把「录制」变成「切面板」）、数字超出
面板数当没听见。每段的悬停提示也写上自己的键，否则这功能对不知道它的人等于不存在。

截图预览的 `Esc` 也是分两段的：正画着标注时第一次 `Esc` 只停笔（工具栏那颗
高亮当场灭掉），再按一次才收走面板。跟系统里"先取消当前选择"的习惯一致，
也避免手一抖整个面板连带刚圈的那几笔一起没了。

「丢弃」没有配键（那些菜单项一律 `keyEquivalent: ""`）：它是这条流程里唯一
不可逆的动作，必须点一下。

用 Carbon `RegisterEventHotKey` 注册：不需要辅助功能权限、不需要 Input Monitoring，菜单栏应用在没有 key window 时也能收到事件。

### 菜单栏：一枚图标 + 八行菜单

图标是**自己画的**：一副四角括号，和截图时浮在屏幕上那副是同一个形状。
以前用的是系统货架上的 `camera.viewfinder` —— 截图类 app 一半在用它，
装在菜单栏上认不出是谁。三份状态共用这副括号，只换中心那点东西：

| 状态 | 长什么样 | 什么时候 |
|---|---|---|
| 常态 | 空心的四角括号 | 平时 |
| 拍到了 | 括号中间多一颗实心点 | 每次截图之后闪 0.18 秒 |
| 缺权限 | 括号中间一个感叹号 | 屏幕录制权限没授上 |

三份都是模板图（`isTemplate`），浅深底和"用强调色"由系统自己解算。
"闪一下"以前是**整枚符号换掉**（换成 `checkmark.circle`），那读起来像换了个 app，
而不是"这一下拍到了"。

菜单每次弹出整份重建，一共 **8 行动作**（瘦身前 16 行：14 条动作 + 2 行提示）：

```
截图　·　⌃⌥A
截图文件 ▸　路径说明 / 最近那几张 / 打开保存位置
登录后自动启动（含崩溃后自动重启）
屏幕录制权限：已授权 / 未授权（点此修复）
设置…　·　⌘,
退出 Grabi　·　⌘Q
```

删掉的那几行各有各的去向，不是"就是没人管了"：

- **两行提示**（手势说明、保存路径）：手势那句覆盖层顶部本来就有一条；
  路径那句挪进「截图文件」子菜单，它跟着"文件"这件事走更顺。
- **「打开保存位置 / 最近截图」两条**并成一个子菜单：
  两件都是"对已经存下来的那堆东西做点什么"。
- **「开机自动启动」和「崩溃保活」并成一条**：它们本来就是同一个不变式的两面
  （保活 ⇒ 自启），摆两条等于允许用户拧出一个自相矛盾的组合，再靠代码背着他掰回去。
  判断抽成 `SettingsStore.autoStartPair(turningOn:)`，菜单和设置窗**共用这一份**。
- **「隐藏菜单栏图标」挪进「设置 ▸ 界面」**：那是一条按下去就把这个菜单本身藏掉的键，
  放在菜单最下方反而最容易被误按。
- **「关于 Grabi」删了**：版本号一年变不了几次，不值得占一行；它在
  `Grabi ▸ 关于 Grabi`（app 激活时顶部那排）里，走系统自带的关于面板，
  版本从 `Info.plist` 读，app 里不用抄第二份。这一条去处有断言盯着。

「截图文件」子菜单里**一张已经不在盘上的照片都不会摆**：摆三条按下去打不开的路径，
比不摆更糟。显示层过滤掉的，偏好里也同步清账。

### 为什么菜单栏应用也要有主菜单

LSUIElement 应用不写主菜单，代价远不止"顶部少一排菜单"：⌘C / ⌘V / ⌘A 这些
**标准编辑快捷键是由主菜单的 key equivalent 派发的**。没有主菜单，设置面板里的
文件名输入框就粘贴不进去；而 app 一旦被激活
（打开设置、弹权限说明），顶部还会出现一排只有光秃秃应用名的空菜单。

所以 `MainMenu.install()` 补了一份精简但符合惯例的：应用 / 编辑 / 窗口。

截图预览面板的 ⌘C 不受影响：菜单项的启用状态走响应链验证，面板里没人响应 `copy:`，
菜单项保持禁用，事件于是照常落到 `PreviewPanel.keyDown`。同理，⌘W 在无边框面板上
被 `performClose(_:)` 接住并转成"收走面板"——**不能**让菜单直接关窗，那样会绕开
`dismiss()` 的清理，压暗层和点击监听就永久留在屏幕上了。

## 自启动与后台保活

| 开机自启 | 崩溃保活 | 走哪条通道 |
|---|---|---|
| 开 | 开 | `SMAppService.agent` + bundle 内 plist |
| 开 | 关 | `SMAppService.mainApp`（系统登录项） |
| 关 | 关 | 全部注销 |

保活会隐含开机自启——保活的前提是程序在运行。

这条不变式以前只写在两个开关的事件处理里：**默认值本身是违反它的**
（`keepAlive=true`、`launchAtLogin=false`），所以设置面板一打开就画出
"保活开着、开机自启没勾"，而它上面那行字明明写着"会一并开启开机自启"。
现在 `SettingsStore.impliedLaunchAtLogin`（纯函数，`--logic-selftest` 查它的四行真值表）
+ `normalizeAutoStart()` 在启动和 `refresh()` 时各归位一次，
上面那张表里的「关 + 开」组合不再是可达状态。

界面上现在**没有两个开关了**：菜单栏和「设置 ▸ 运行」各有一条
「登录后自动启动（含崩溃后自动重启）」，按一次两条偏好一起动。
判断只有一份（`SettingsStore.autoStartPair(turningOn:)`，`--logic-selftest` 查它
"不存在开一条留一条的第三种输出"），两处各写一遍"顺手改另一条"迟早会有一处先漂。
上面那行「开 + 关」因此只能来自**老库**（拆着摆那阵子存的），
`normalizeAutoStart()` 负责把「关 + 开」那种违反不变式的存值掰回来 ——
它不掰「开 + 关」，那是用户当初真选过的组合，背着他打开保活等于替他做决定。

「运行」面板下面那行状态也不该只报事实。它原来长这样：

> 当前机制：未启用　·　系统未找到记录（app 可能被移动过，重开一次即可）

一行**灰色小字**。两个开关都勾着、系统其实根本没登记，界面仍然用陈述语气写在最不起眼
的地方，也不给出路 —— 而同一个面板往下两行的「屏幕录制权限」早就是橙色「未授权」+
「修复权限」按钮了。判据现在收进 `AutoStartManager.advisory(...)`（纯函数）：

| 用户要求自启 | 系统状态 | 那行怎么写 | 按钮 |
|---|---|---|---|
| 否 | 未启用 | 灰色陈述 | — |
| 是 | 没登记（机制 `none`） | **橙色 + ⚠︎ 开关开着但系统没登记** | 重新登记（`apply(force:)`） |
| 是 | 已注册、等确认 | **橙色 + ⚠︎** | 打开登录项设置 |
| 是 | app 不在 `/Applications` | **橙色 + ⚠︎ 拖过去再说** | 无（得用户自己拖，按钮点了也不变） |
| 是 | 已托管并启用 | 灰色陈述 | — |

`--logic-selftest` 逐行查这张表：醒目度、按钮种类，再加两条通用规则 ——
"有出路就必须有按钮标题"（一个不写字的按钮比没有按钮更糟）、
"变橙必须带 ⚠︎ 说明 / 没事不许挂 ⚠︎"。反向对照分两次：判据退回"只有目录警告才变橙、
永远不给按钮"，中间两行立刻报 `✗ … 醒目度 false，应为 true；出路不对，得到 none`；
只把「重新登记」的标题改成空串，报 `✗ … 有出路却没按钮标题`。

顺带修掉一个条件写反：`locationWarning` 原来还要求"已经有机制在跑"才提示，
于是"没登记 + 不在标准目录"这种最该提醒的情况反而一句提示都没有。

最后一行才是这次改动的分寸所在：**健康安装下那行仍然是灰色一句话**，
离屏渲染实测面板高度和改之前一样（620×356）。把警告做成常态，等于没有警告。

### 「重新登记」到底算不算成功

`force`（刷新签名登记）这条路以前会**谎报成功**：

```swift
if force, isArmed(service.status) { try? service.unregister() }   // 失败被吞掉
if !isArmed(service.status) { try service.register() }            // 于是被跳过
```

注销失败时状态仍然算"挂着"，第二行的 `register()` 就被跳过，函数却回报 `true`，
`apply` 顺手把**新的二进制指纹**写进 UserDefaults —— 于是"签名变了要重新登记"这件事
从此永远不会再试。这条路不是摆设：每次重新编译安装都会走它（`syncFromSettings`
发现指纹变了就 `force: true`）。系统那边还指着旧登记，下次登录要么拉不起来，
要么 `job state = spawn failed` / `EX_CONFIG`。

现在决策抽成
`AutoStartManager.register(force:armedBefore:unregister:register:armedAfter:)`，
系统调用注入进来，两条硬规矩：**注销失败就是失败**，以及**收尾必须回读系统状态才算数**
—— 没抛异常不等于挂上了，SMAppService 收下请求却没留下记录是可能的。
`--logic-selftest` 用一台假状态机跑**同一个函数**（不是抄一份逻辑去对答案），六行：

```
  ✓ 没催 force · 系统已挂着
  ✓ 没催 force · 还没登记
  ✓ 催了 force · 正常刷新
  ✓ 催了 force · 注销失败
  ✓ 注册直接被拒
  ✓ 注册请求被系统吞掉 → 回读没挂着就是失败
```

除了结果本身，还查**副作用发生的次数**（"注销失败"那一行必须是"注册调了 0 次"，
否则就是偷偷接着往下走）和"失败原因这句话能不能直接进对话框"（非空、不含换行）。
两次反向对照各只改一处：吞掉注销的错误 → `✗ 催了 force · 注销失败 ← 结果 refreshed`；
去掉回读那条 guard → `✗ 注册请求被系统吞掉 ← 得到了 registered`。

顺带补了两处静默：`registerAgent` 失败以前只写日志（`registerLoginItem` 倒是会弹框），
现在两条通道都会说话；bundle 里缺保活 plist（安装包坏了）也不再是"点了开关没反应"。

plist 里的保活语义是：

```xml
<key>KeepAlive</key>
<dict><key>SuccessfulExit</key><false/></dict>
```

只有**异常退出（崩溃）**才重启。用户从菜单点「退出」是 `exit(0)`，不会被系统拉起来。若写成 `KeepAlive = true`，主动退出会被立刻复活，体验很糟。

## 命令行自检

> 下面是按时间倒序保留的开发记录，用来防止同一个坑踩第二次。**除本节开头的入参说明外，
> 各条记录写的是"当时改了什么"，不代表当前代码仍然长那样** —— 例如与已删除的编辑面板
> 有关的段落，都是那一版的实现快照。

```bash
BIN=/Applications/Grabi.app/Contents/MacOS/Grabi

$BIN --diagnose        # 环境、权限、显示器分辨率、配置、热键注册检测（不报跨进程占用）
$BIN --help            # 参数清单（热键两行从当前设置读，不手写）
$BIN --shot            # 立刻截一张全屏图并落盘，打印分辨率与耗时
$BIN --ocr-selftest    # 自己画一张中英文图再识别回来（不需要截图权限）
$BIN --logic-selftest  # 纯逻辑，33 组。组名不抄在这儿：抄一份就会和代码里那些 noteGroup 分家（历史上真分过），跑一遍看得到全部组名
$BIN --agent status    # 自启动各通道的原始状态
$BIN --ui-render /tmp/ui   # 离屏渲染界面组件，不依赖屏幕录制；有红行退 1
$BIN --ui-preview /tmp/p.png  # 把预览面板真的摆到屏幕上再自拍一张（需要显示器亮着）
```

参数不认识时**报错并退 2**，不再照样把菜单栏 app 拉起来。之前一次编译失败留下
旧二进制，`--geometry-selftest` 打进去后被当成"没有这个分支"，GUI 静启动，
终端看上去像卡了七分钟。自检入口就该对参数严格：报错误报得像错误。

两套自检现在**都给退出码**。`--logic-selftest` 一直有，而 `--ui-render` 以前不管
多少行红都 `exit(0)` —— 一个只会打字的自检当不了闸门：脚本、CI、或者下一个只跑
一次的人，都会把"跑完了"当成"跑对了"。改法是把那一份文件里 83 处 `print` 全部
改走一个 `say()`，顺手数 `✗`（红）和 `△`（未验到），结尾按红行数决定退出码；
`△` 只报不失败（它说的是"这块没验到"，不是"这块坏了"）。

结论行刻意不带 ✓/✗/△ 这些记号：它自己带一个 `✗` 的话，"红 N 行"和外面
`grep -c ✗` 就永远差一行，而差的正好是它自己 —— 这两种数法迟早会有人拿去对账。
`--logic-selftest` 的结论行同样处理。对照：造 1 行红 → 退出码 1 且计数与 grep
都是 1；只造 1 行 `△` → 退出码仍是 0。

`--ui-render` 是这一轮改交互时最值钱的工具：工具栏各形态、结果角标、压暗层、
文字层高亮、**四个设置面板**、**就地预览面板**和**选区覆盖层的五个状态**都按真实视图画成 PNG。
它不只出图，还出数字：面板排版完会打印「内容需要多高 / 窗口给了多高 / 有没有哪节塌了、
哪行超宽」，覆盖层数「强调色像素有多少」。
当场揪出这些只看得见才发现的问题：

- 边框的白色内描边被父视图 `masksToBounds` 整条裁掉；四角手柄被 8pt 圆角削掉一片；
- 设置面板四个节全部塌成标题那 16pt（根因：控件工厂没关
  `translatesAutoresizingMaskIntoConstraints`，直接 `addSubview` 的小标题被
  AppKit 按旧 frame 和新约束两套解，冲突时被静默 break）；
- 选区覆盖层的描边和尺寸标签画在选区**外侧**，于是「整屏」候选（选区就是整块屏）
  四条线一条不剩、标签直接飞出屏幕外 —— 那个状态下画面只是变亮，没有任何反馈。
  现在描边一律画在内侧，标签夹回屏内，断言报 `11672 强调色像素 ✓`；
- **「说了没做」**：提示条和代码注释都写着「⌥ 以按下点为中心向外扩」，代码里却只是
  把位移乘 2 —— 按下点仍然是角。现在由 `selectionRect` 真正以按下点为中心成形，
  并加了几何断言：`⇧ → 120×120 ✓`、`⌥ → 中心 (400,400) == 按下点 ✓`
  （把 `selectionRect` 改回旧写法，第二条立刻报 `✗ 按下点还在角上`）。

- 顺带修掉一类反馈时机问题：就地预览的「识别选区 / 保存 / 清除选区」原来
  **什么时候都能点**，没框选就点只会换出一句状态行解释。现在按「有没有选区 /
  有没有结果 / 是不是在识别」灰掉 —— 灰掉比"点了才知道不行"早一拍，而且灰掉的
  NSButton 连 `⌘R` 这类 keyEquivalent 都不触发，识别途中连点也不会堆出并发任务。
  禁用态在图上几乎看不出来（浅色底下尤其骗人），所以这条走的是读 `isEnabled`：
  `空面板可点：识别全文 ✓`、`框选+有结果后五个动作全部恢复可点 ✓`。

- **工具栏分组读不出来**：预览条上有两到三个语义组（动作 / 去留决定 / 收起），
  原来组之间只塞了一个 6pt 的空隙视图 —— 那个纯图标的「收起」于是被读成
  「丢弃」旁边又一个动作，而一个决定图片去留、一个只是把条子收起来。
  现在换成 1pt 竖分隔线（这条栏是固定深色的 HUD，所以线也用白色半透明；
  用 `separatorColor` 在这块底上几乎看不见，看不见就等于没分）。
  检查也跟着做成断言：`toolbar-normal / ocr / failure` 三种形态各 2 条分隔线，
  且「收起」前面必须就是那条分隔线（把分隔线换回空隙，报
  `✗ toolbar-normal：分隔线 1　最后一个按钮前是 NSView`）。

- **悬停时那颗强调色手柄被削平**：预览条四角和四边中点的 8 个手柄，圆点内缩 6pt
  是照**静止那一号**（10pt，半径 5）算的，而悬停/拖动会放大到 16pt（半径 8）再加
  3.5pt 投影 —— 这一层被父视图 8pt 圆角 + `masksToBounds` 裁着，于是**恰恰在最该
  显眼的那一下**，圆点外侧被边界削成平的。内缩改成按最大那一号算（11pt）。
  检查也是量几何不是看图：`knobOverflowForSelfTest` 把 8 个手柄 × 常态/悬停
  两种尺寸的绘制矩形全算一遍，改之前报
  `✗ 8 个会探出边界被削平 → 悬停 topLeft，悬停 top，…`，改之后 `8 个手柄 × 常态/悬停 全部 ✓`。
- **同一个 bug 在调整选区覆盖层的翻版**：那里四颗圆点直接压在选区角上，整张选中（这是常态）
  时圆心正好落在视图边界 → 左右两颗被裁成半圆；选区描边还往外扩了 0.75pt，
  贴边那两条 1.5pt 的线被裁成 0.75pt，看着像断线。圆点改成夹取圆心
  （`clampedHandleCenter`，静态纯函数，自检走同一条算式而不是抄一份），描边改画内侧。
  断言两条：`整张选中时 4 颗圆点全在视图内 ✓`（把夹取改成原样返回 → `✗ 探出 4 颗`）
  和 `不贴边的圆点原样不动 ✓` —— 后者在同一个反向对照下**仍然通过**，
  说明这两条查的确实是不同的事。

顺带做过的一致性体检：全量提取用户可见文案比对术语，改掉一处漂移
（同一功能在菜单栏叫「不弹预览」、在设置里叫「不弹卡片」，"卡片"是上一版结果卡片的残留）；
按"能放几行"重算了一遍文案宽度，抓到**首次运行那条引导被截断** ——
它长 317.8pt 而说明行只有 272pt（那是**恒按有缩略图**算的宽度，引导卡根本没缩略图），
于是新用户第一眼看到的指示是半句「先点菜单栏的 Grabi 图标授权屏…」。
现在说明行按有无缩略图分别算宽（336 / 272）并允许折两行，卡片高度跟着长
（两行时 56 → 66，断言 `✓ 会跟着长高`）；
同名文件撞车确认有 `-2/-3` 递增后缀不会覆盖；白字压在 0.68 黑提示条上，
最坏情况（纯白桌面）仍有 7.7:1 对比度。

断言本身也要验：把上面两处改回旧写法各跑一次，确认它们会变红
（`Δ-0.149 ✗`、`2340 强调色像素 ✗`），否则一条永远通过的检查等于没有。
同一套图现在**深浅两种外观各画一遍**。张数不在这里写：它由「出图清点」那一节自己打，
那一节逐张对账「想画的、写成的、盘上真有的」三本账，还确认深浅两遍是同一批文件名。
上一版这里手抄过一个数，抄完就开始漂 —— 现在这句里不留数字。W2 给工具栏添的是
`toolbar-*-kept.png` 五张：「已保留」那颗禁用按钮只有真画出来才看得见。第一版的浅色通道是假的 ——
只设了 `NSApp.appearance`，抓图时动态色仍按系统默认解算，浅色拍出来还是深色，
看不出来也很正常，因为"两张一样"不像一个 bug。现在抓图统一包在
`performAsCurrentDrawingAppearance` 里，并加了一条**外观对账**：同一张设置面板，
浅色通道的平均亮度必须明显高于深色通道（实测 0.235 → 0.899），差值不够就报 ✗。
这条检查上线后立刻查出结果面板把 `underPageBackgroundColor` / `textBackgroundColor`
**在建视图那一刻冻进了 layer** —— 用户一天里浅色↔深色自动切换后那块底色不会跟着变。
自检还顺带做四遍体检：

1. **朗读名**：图标按钮和自绘交互视图必须有 `accessibilityLabel`。需要名字的控件
   **18 个，缺 0 个** —— 选区覆盖层、预览图、文字层、调节手柄、结果角标这些整块
   自绘的视图，读屏用户点上去原来只听到"组"两个字。
   （这个数上一版曾报 26/27，那是**虚的**：四个设置面板往清单里塞的是同一个
   `window.contentView`，于是一个面的控件被数了四遍，另外三个面一个都没走到。
   清单现在收各面板**自己**的视图树，并且加了一道"根不许是同一个对象"的闸门。
   另外四个面各有一条状态行 —— 平时是空串，只在真有事可说时才有内容，所以读屏
   用户如果不知道有这一行，就永远听不到「没写成功」「按了取消」这类提示；现在
   每个都带显式朗读名。）
2. **菜单结构**：主菜单 + 状态栏菜单逐条查连续/开头/末尾的分隔线、空标题、
   "可点却没有任何动作"、同一组合键挂两个动作。**报数只报不随环境变的那一半**：
   裸二进制恒为 40 项，装机版是 40 + 「截图文件」里那些照片行的条数 —— 那截是每次弹菜单
   现算的（`pruneRecentShots { fileExists }` 会把文件已经不在的剔掉），所以同一个
   装机版一分钟内量到过 51 和 52 两次。它涨落不是回归，**要盯的是「问题 0 项」**；
   「查找」那 6 项（父项 + 5 条）两边都算进去了。
   状态栏那份菜单是**每次弹出整份重建**的，它的问题全是动态的，不"真的弹开一次"
   看不见。
   这条一上线就顺手挖出一个 AppKit 老坑：`NSMenuItem()` 的默认标题不是空串，
   是类名字面量 `"NSMenuItem"` —— 菜单栏因为显示子菜单标题才没露馅，但按标题找
   东西的代码全会踩到，于是三个顶层项改成显式给名。
3. **纯图标按钮的悬停提示**：4 个纯图标按钮，缺提示 0 个。朗读名管的是 VoiceOver
   用户，鼠标用户靠的是悬停那一下 —— 只有图标、既不说话也不提示的按钮只能靠猜。
4. **布局越界**：走一遍视图树，找被父视图切到的控件 —— 设置四个面板的
   **默认尺寸和允许的最小尺寸**，深浅两套外观各跑一遍。
   这一条是补出来的：以前只画默认尺寸，等于"用户把窗口拖小之后长什么样"从来没人看过。
   判据只盯**横向**（±1pt），纵向放过 8pt —— 第一版什么都不知道，一口气报了 8 处，
   全是 `NSButton` / `NSSlider` 的 bezel 比行的对齐矩形探出 2~4pt，还有一条
   `NSSliderKnob 越出 NSSliderTrack`（滑块的旋钮本来就该比轨道大）。
   那是 AppKit 的正常行为：**一条天天误报的检查，明天就会有人直接忽略它的红**。
   现在改成量控件的对齐矩形、不钻进控件内部，横向超 1pt 或纵向超 8pt 才报。
   检测器自己也被验过：每次跑完往容器里塞一个明知越界的视图，看它抓不抓得到
   （`✓ 自检探针：故意摆一个越界视图，被抓到了`）—— 这一条当场查出"最小尺寸那一趟
   被放在 `guard emitChecks` 后面，浅色通道根本没画过"，两套输出的张数才会 25 / 24 对不上。

前三条都反向验过：把说明行做成可点、把 `toolTip` 那一行注掉，立刻分别报
`✗ …「移动选窗口…」可点，但没有任何动作`（两条）和 `✗ 缺提示 4`。
组合键那条还修过一次**误报**：只看 `⌘Z` 会把「撤销 ⌘Z / 重做 ⇧⌘Z」报成撞车 ——
一条会误报的检查，很快就不有人信了，所以判据里必须带上 ⇧⌃⌥。

顺便还查出一个**指标本身**的错：控件清单是两套外观各收一遍的，"需要名字的控件"
从 14 被数成了 28。第一版照着 28 写进了文档 —— 只取第一遍之后才是真数。
局限也要说清楚：它验的是视图本身 —— 投影（真窗口的那种柔和落影）和多窗口在真实
桌面上并排时的对位，仍然只能在亮着屏的真机上看。浮层的**先后顺序**和**落位**这两件
以前也只能真机看的事，现在拆成了可在 `--logic-selftest` 里跑的断言（见下）。

`--logic-selftest`（原名 `--geometry-selftest`，随着覆盖面变大改了名）补的是另一条命脉：**区域截图的坐标换算**。多显示器上
`rectInScreen` 是全局坐标（原点主屏左下），而抓到的 `CGImage` 原点在该屏左上，
两者必须同时换算 —— 少减一次 `screen.frame.origin`，裁出来的矩形会整体偏移一个屏宽：
轻则裁到图像外，重则**静默裁到另一块内容上**并正常存盘。这种 bug 靠肉眼看主屏永远
发现不了，所以直接对手算的坐标表和一张「缓冲前半红、后半蓝」的合成位图断言：

```
主屏·贴顶                    → (0,200,200×200)   ✓
右侧副屏·贴该屏左边缘        → (0,980,200×100)   ✓
屏幕上半 → 像素 R=255 G=0 B=0（应为红）          ✓
```

两组都做过反向对照：把 `- screenFrame.minX` 去掉，只有副屏那条报
`✗ 得到 (1440, 980, …)`；把 `crop` 的翻轴写成 `normalizedRect.minY`，
两条像素断言立刻互换颜色（`✗ 屏幕上半 → R=0 G=0 B=255`）。
像素那两条是真的走 `CGImage.cropping` 后读缓冲区第一个像素，
合成图也不经过 `CGContext`，免得用绘图翻转去验绘图翻转（自己验自己）。

同一个入口现在还管**窗口位置记忆**（`WindowFrameMemory`）：设置窗口和识别面板
原来每次启动都 `center()`，用户拖过去的位置一次重启就没了。两个坑要避开：

- **记左上角，不记 `frame.origin`。** AppKit 的原点在**左下**，而设置窗口的高度是
  按当前面板现算的（`showPane` 保持顶边往下长）。存左下原点的话，上次停在更高的
  「快捷键」页 → 原点更低 → 下次打开落在矮的「保存」页，窗口整块往下掉一截，
  用户看到的是"记错了"。存了 `top` 之后自检里那条往返断言直接抓这个错：
  故意改存 `frame.minY` 就报 `✗ 原点 (333, 16)`（应为 `(333, 222)`）。
- **恢复前先问这个位置还在不在屏幕上。** 上次放副屏、今天拔掉副屏，窗口会落在一片
  不存在的坐标里，标题栏看不见也抓不着，用户只会觉得"设置打不开了"。所以判据是
  「标题栏那一条有没有被某块屏的可见区接住」，接不住就居中。垂直方向按**顶边**夹
  而不是按整块夹 —— 按整块夹会把顶边压到菜单栏底下，那是更糟的错；窗口比屏幕还高
  时宁可底下溢出，也要保住标题栏可抓。
  把「接不住就居中」这条保护去掉，`拔掉副屏：…交给居中` 那条立刻报
  `✗ 得到 (1500, 710)　期望 nil（居中）`。

设置窗口的**初始尺寸**是这一轮补的另一条：原来一律开 1000×660，从不看屏幕。
13 寸上没问题，接到 800×500 的投影仪或 Sidecar 上，一开就比整块屏还大 ——
而窗口位置的夹取保的是标题栏（宁可底下溢出），用户看到的是"窗口跑出去了、拖不回来"。
现在按鼠标所在屏的可见区收一收，收完也不许低于最小尺寸（宁可溢出，
也不能把工具栏那排按钮挤断）：

```
  ✓ 13 寸 1440×900　可见区 1440×900 → 1000×660
  ✓ 1280×720　可见区 1280×720 → 1000×660
  ✓ 投影仪 / Sidecar 800×500　可见区 800×500 → 752×452
  ✓ 1024×640　可见区 1024×640 → 976×592
  ✓ 比最小尺寸还小的 640×480　可见区 640×480 → 720×440
```

反向对照就是把 `initialSize` 改回"一律返回 preferred"：后三行立刻报
`✗ … 还是比可见区宽；还是比可见区高` —— 这也顺便证明了那个缺陷是真的存在，
不是想象出来的。

还有一组是**文件名模板**（`SettingsStore.sanitize`）。原来只把
`/\:*?"<>|` 和换行换成 `-`、空串退回 `Grabi`，还漏了三件会真出事的事：

- **前导点**：模板写成 `.截图` 会存出隐藏文件 —— 用户只看得到"截图不见了"，
  Finder 里搜不着。现在开头连续的点一律剥掉，尾部的点也剥（否则加扩展名后是 `名字..png`）。
- **长度**：APFS 单个路径成分上限 255 字节，而这里还要留扩展名和同名撞车的 `-2`/`-3`。
  超预算就截，截断按 `Character` 走 —— 按 UTF-8 计数硬切会把 emoji 劈成乱码。
  断言里两条就是量这个：`200 个汉字 → 60 个 = 180 字节 ✓`、
  `59 个汉字 + 👍 → 宁可少留一个字 ✓`。
- 清洗动过用户写的东西，**设置面板当场说** —— 但只说**真做过的那几件**。原来只要
  "展开后 ≠ 清洗后"就整句报「非法字符已换成 -，超长已截断」：只是超长的模板会被说成
  连字符也被改过，开头带点的也一样。这句本身就是不诚实的提示，而提示一旦掺假，
  用户就不会再信它。现在拆成五项独立判（未知占位符 / 非法字符 / 开头的点 / 末尾的点 / 超长），
  其中"超长"按字节预算判而不是比长度 —— 去掉一个点同样会让长度变短，
  那样「开头的点已去掉」会顺带把「超长已截断」也报出来。
- **不认识的 `{...}` 现在会点出来**：`{datetme}` 这种笔误以前原样落进文件名，
  用户只觉得"名字怎么怪"，猜不到是自己少打了一个字母。示例行现在报
  「未知占位符 {datetme} 会原样写进文件名」，而且示例里真的带着那串 —— 说的是看得见的东西。
  可写的占位符只有一份真相：`SettingsStore.knownPlaceholders`，面板上那行
  「可用占位符：…」由它拼出来，改名忘了同步会当场报红。
  自检为此多了一组 14 行：七个未知占位符用例（`{}` 算、未闭合的 `{没闭合` 不算、
  重复只报一次）加六个"动了哪几刀"用例。两次反向对照：让 `unknownPlaceholders`
  永远返回空 → 四行报红；把"超长"退回"只要名字变过就报" → `a/b:c`、`.隐藏`、`尾巴.`
  三行各多出一句「超长已截断」而报红。

这一组顺带挖出一个真的布局 bug：示例行原来和 250pt 的输入框挤在同一行，
它的固有宽度会把整个设置窗往上顶 —— 填一个长模板实测窗口从 620 撑到 **894pt 宽**。
改成示例单独一行后宽度回到 620，面板高度跟着折行数自己长（`余量 +0 ✓`）。

**检查本身也要验**，这一轮抓到两次：

- 第一版量的是示例行的**宽度**，而它允许折行，`fittingSize` 就把"给了多宽"原样还回来，
  永远 `余量 +0` —— 一条不可能失败的检查。改成量**高度**（按当前宽度算需要几行）之后，
  它当场报了 `✗ 竖向被切：需要 91 给了 28`。
- 把示例塞回同一行做反向对照，宽度检查立刻报 `✗ 窗口宽 894`；
  而先前为"顶宽"加的两条抗压设置在改成独立一行后已经不需要，删掉了 ——
  留着会让下一个人以为那是必要的。

还有一组是**失败反馈**。截图失败原来弹一句 `截图失败 / 写入文件失败：<系统原话>`
加一个「好」字按钮 —— 把问题原样丢回给用户。现在每条错误都带一句"接下来做什么"，
能一键去解决的还把那个动作做成**默认按钮**（回车就是它）：

| 错误 | 说明 + | 默认按钮 |
|---|---|---|
| 缺少「屏幕录制」权限 | 勾选后必须重启一次 app 才生效 | 去开启权限（跳系统设置面板） |
| 写入文件失败 | 多半是目录被删/挪走/磁盘满 | 换个保存位置（开设置窗口） |
| 找不到可用的显示器 | 唤醒显示器再按一次热键 | 再试一次 |
| 目标窗口已关闭 / 裁剪失败 | 说明为什么、再来一次就好 | 只有「好」 |
| 选区太小（用户主动放弃） | 什么都不弹 | — |

断言查的是映射本身：每条真会发生的错误都得有恢复说明、`recovery` 与按钮标题
必须同时有或同时没有、说明不能和错误本身重复、长度 ≤ 60 字（否则对话框糊成一块）。
反向对照：把一条说明改成 `nil`、把 `retry` 的标题改成 `nil`，报
`✗ … ← 没有恢复说明` 和 `✗ … ← 有动作却没按钮，或有按钮没动作`。


最后两组断言管的是**浮层之间的关系**。这类知识以前只写在注释里，而注释不会失败。

- **层级顺序**（`ShotLevels`）：压暗层 < 预览面板 < 工具栏 < 结果角标 < 全屏覆盖层。
  六个 `window.level =` 全部改成从这个入口取值，「工具栏跑到预览面板底下」这种错
  就不只是「读过注释的那个人才防得住」。反向对照：把预览和工具栏的常量对调，
  立刻报 `✗ … ← 预览面板 没有低于 工具栏`。
- **工具栏落位**：`InlinePreviewController.toolbarOrigin` 抽成纯函数后，7 种摆法
  都能直接断言落点在可见区内 —— 预览居中、贴屏底、贴屏顶、800×500 小屏、
  工具栏比屏还宽、比屏还高、原点不为 0 的右侧副屏。三条护栏各自反向验过：
  去掉「比屏还宽就贴左边」报 `✗ 落点 (-108, 48)`（整条栏跑到屏幕左边外面，
  用户只剩快捷键可用）；去掉底边兜底报 `✗ 落点 (120, -220)`。
  顺手记一条**自我纠正**：先前还加过一条「预览压到菜单栏之上」的垂直夹取和配套用例，
  后来确认 `currentRect` 在别处已被夹进 `visibleFrame`，那条分支永远进不去，
  于是连用例一起删了 —— 自检里留一条走不到的分支，等于给下一个人埋雷。
- **不再自动并成标签页**：设置窗口设了 `tabbingMode = .disallowed`。系统默认会把
  同一 app 的有标题窗口自动并到一组标签里。

**像素密度元数据**（`ScreenGeometry`）是这一轮里最不像“UI 问题”的一个，但后果看得见：
写盘时 DPI 取的是 `NSScreen.main` 的倍率，而那是**当前有键盘焦点的那块屏**，不是被截的
那块 —— 在外接 1x 显示器上截一张图，文件头会被打上 144dpi，插进文档就凭空大一倍。
现在倍率按选区所在屏算（中心落在两块屏之间的空档时，按重叠面积取占大头的那块），
预览角标那句「2880 × 1620」和文件里的 DPI 也从两份写法并成一份。

第二条更隐蔽：预览里改选区重截走**覆盖写**，而那条路一个
DPI 属性都不写 —— 同一张截图裁一刀就打回 72dpi，尺寸突然翻倍。现在覆盖前先把原文件
自带的 DPI 读回来带上（原文件没标注就不猜，保持不标注）。往返两头都断言：

```
覆盖写前 144dpi → 覆盖写后 144dpi                    ✓
外接 1x 屏上的选区 → @1.0x　写进文件的 DPI 72        ✓
跨屏·中心落空档，主屏占大头 → @2.0x　DPI 144         ✓
```

反向对照：注掉回带 DPI 那三行报 `✗ 覆盖写前 144　覆盖写后 0`；把倍率解析写死成
「只认第一块屏」报 `✗ 外接 1x 屏上的选区 → @2.0x`、`✗ 跨屏·外接占大头 → @2.0x`。
前半那条（写进去得读得出来）是故意留的：读不到 DPI 的话，「覆盖了没丢」会永远成立。

`ImageWriter.discard` 是同一条原则的另一处：**用户看得见的结果，必须和磁盘上真的发生了
什么一致**。它以前用 `try?` 把 `trashItem` 的错误吞掉，然后照样 `forgetShot`、照样关面板 ——
而只读挂载点、外置盘、被 `chmod` 过的目录上 `trashItem` 是真会报 `NSCocoaErrorDomain 513`
的，于是界面把「已丢弃」演完，文件还原封不动躺在截图目录里，用户只会觉得废纸篓坏了。
现在它 `throws`，`onDiscard` 回一个 `Bool`：没真的移走就**不撤面板、也不清剪贴板**，
弹框把原因和完整路径一起给出来，默认按钮是「在访达中显示」，让你自己删。

四条断言跑在临时目录里一个 `0o500` 的子目录上（那个目录真的丢不掉东西，不是编出来的用例）：

```
  ✓ 丢不掉时抛错
  ✓ 抛错的同时文件确实还在原处
  ✓ 已经不在了不再报失败
  ✓ 说明里带上原因和完整路径（只说「没权限」还得自己找文件）
```

反向对照**分两次**跑，光这一件事就抓到一条检查自己不够尖：第一次把 `discard` 退回 `try?`，
只有第一条报 `✗`，而「已经不在了不再报失败」跟着一起绿 —— `try?` 把"文件不存在"的错误
也吞了，那条断言在那个版本里根本分不出对错。第二次保留 `throws`、只去掉"已经不在就早退"
那一行，它才如实报 `✗ 已经不在了不再报失败`。一次只改一处、逐条读结果，否则很容易误以为
四条都被验过了。

「成功移进废纸篓」那条**故意不跑**：自检不该往用户的废纸篓里塞一个文件，而这个分支本来
也没被这次改动碰过。

同一个毛病在**识别文本旁车 `.txt`** 上还有一处，一并修了：设置里勾着「保存识别文本」，
而写旁车那里只写日志、错误被吞掉，角标照样弹"已识别 N 行文字"，用户接着就会去
截图目录找那个根本不存在的 `.txt`。现在它说真话：保存时把角标那行说明换成
`已存 shot.txt` 或 `shot.txt 没写成功：<原因>`（写成了才显示"按住拖动即可划选"）。
措辞抽成 `ImageWriter.ocrTextStatus`，自检两头都查：只读目录里
`✓ 写不进时抛错，且不留下半个 .txt`、能写时 `✓ 真的落盘（读回来对得上）`，
外加"失败那半句绝不出现「已存」"、"两句都得是单行"。
反向对照把 `writeText` 退回 `try?`，第一条立刻 `✗`。

还有一处是**键根本没接上**：识别面板的 Esc 长按不发。这个面板的动作原来全靠
`keyEquivalent`（⌘R / ⇧⌘R / ⌘S / ⇧⌘C / ⌘D 都有），只有 Esc 没人管 —— 而它是
用户画错框后最本能的那个键。修的时候踩到一个 AppKit 的坑：先按标准做法重写
`cancelOperation`，编译过、看着没错，实际还是不响应，因为右边那块识别结果是
`NSTextView`，它自己就消费 Esc（结束查找的内部状态），事件到不了窗口。改成
窗口作用域的 `addLocalMonitorForEvents(matching: .keyDown)`，判 `event.window === self.window`
才处理，别的面板按 Esc 不会被误抢。

语义做成两段（`escapeAction(hasSelection:)`，纯函数、进断言）：有框选时先撤框选，
没有框选时才关面板。顺序反了的话，用户画错框一按 Esc，整个面板连带识别结果就
一起没了。

```
    Esc 键（撤选区 → 关面板）
      ✓ 按键监视已装上
      ✓ 第一次 Esc 只撤掉框选，面板还在
      ✓ 第二次 Esc 关掉面板
      ✓ 关窗时监视已摘掉（不泄漏）
      ✓ 两段顺序没写反
```

三条反向对照，一次只改一处：删掉监视器安装 → 只有第一行 `✗`；把 `escapeAction`
改成恒返回 `.closeWindow` → 第二、第五行 `✗`；去掉 `windowWillClose` 里的
`removeMonitor` → 只有第四行 `✗`。第四行查的是本地监视器**不摘就永远在**：它注册在
进程全局的监视器数组上，每开一次面板漏一个，而每个漏下的闭包都在按任意键时被调一次。
自检里"按下 Esc"是直接调 `escapePressed()`，不是模拟按键 —— 模拟事件要靠真窗口和真
runloop，离屏渲染里造不出可信的事件流，那样绿了也不算证明。

同一套键的缺口在设置窗上还有一处：顶部那排面板切换没有 `⌘1…⌘4`。接上之后照例给
它配断言，而**这次是断言自己先露了馅**。第一条查"按键事件进不进得了窗口"，写法是
造一个 `⌘N` 事件丢给 `window.sendEvent`，然后看 `selectedSegment` 有没有变成 `N-1`。
跑反向对照（把 `sendEvent` 重写整个废掉）时，输出是：

```
      ✗ 按键事件进得了窗口、四个面板都切到位（命中 1/4，停在第 1 个）
```

红色是对的，`1/4` 这个数字却不对 —— 键完全没接上，怎么会命中一次？因为测试序列里
有 `⌘1`，而面板**本来就在第 1 个**：那个版本里什么都没发生，判据却满足了。一条在
"坏版本"和"好版本"里给同样答案的检查等于没有检查；这次它靠别的键侥幸变红，换个
起始面板就能悄悄一直绿下去。修法是让探针先把自己挪到**不是**目标的那一段，
"命中"必须是真实发生的一次切换：

```swift
// 先把自己挪到**不是**目标的那一段：不然「已经停在第 1 个面板上按 ⌘1」也算命中，
// 而那条断言在任何版本里都不会红 —— 键完全没接上时它照样给个 ✓。
switcher.selectedSegment = (digit - 1 + 1) % panes.count
```

加强后同一条对照给出 `命中 0/4`。剩下的四条各自只被自己的反向对照打红：`⌥⌘1` 放宽成
"含 ⌘ 就行" → 只认裸 ⌘ 那行 `✗`；去掉"录制框在收键就让路" → 让路那行 `✗`；去掉
"数字超出面板数"的下界 → 越界那行 `✗`；不给每段写 `⌘` 提示 → 提示那行 `✗`。

最后一条不是装饰：`NSSegmentedControl` 不会像 `NSTabView` 那样把 `⌘` 键显示出来，
只在代码里接了键、界面上一个字都不提，这功能对不知道它的人就不存在。所以每段悬停
提示写成「保存（⌘1）」，快捷键面板底部也补了一行键位总览。

### 识别结果终于能搜索了：⌘F 一组，以及三条被反向对照推翻的假设

设置面板里的文字视图可编辑、动辄上百字，但原先没有任何查找手段 —— 找一处误识别
只能滚动加眼睛。补上 `编辑 › 查找`（⌘F / ⌥⌘F / ⌘G / ⇧⌘G / ⌘E）之后，
牵出三件只有跑对照才知道的事。

**一、`performFindPanelAction:` 是一个 selector 加一个 tag，tag 写错不报错。**
「查找下一个」的 tag 从 2 改成 1，界面不会崩、不会提示，只是**弹出查找条**而已。
所以菜单那一节的断言查的是每条的 `selector + 组合键 + tag` 三样，
而不是"有没有这五项"：

```
    查找菜单（一个 selector + tag 分岔，所以 tag 必须逐条对）
      ✓ 「查找…」  ✓ 「查找并替换…」  ✓ 「查找下一个」  ✓ 「查找上一个」  ✓ 「使用划选内容查找」
    查找菜单 5 项　不对 0 项　✓
```

**二、接了 ⌘F，Esc 就从两段变成三段。** 查找条那个输入框拿着键盘时，
Esc 的惯例是"收起查找条"；上一轮接的监视器会把它抢走，变成"整个面板消失"。
判据没用"系统查找条可见吗"—— 探针量下来它隐藏之后视图还在、`isHidden` 仍是
`false`，拿那个当状态会一直读到假的"还开着"。改成只看公开事实：
**焦点是不是在我们自己的控件上**（查找框是 `NSTextView` 的子类，但不是那块结果视图）。
`usesFindBar = true` 也是这条链上的一环：不设的话弹的是独立的旧查找面板，
焦点根本不会进本窗口，那一行断言立刻 `✗`（对照 F 实测 `✗ ✗ ` 三行）。

**三、本来要加的"跨菜单快捷键撞车"检查，被自己的对照证伪后删掉了。**
想法没错：主菜单的键是全 app 解析的，只按单层菜单查撞车会漏。动手的对照是
「给『查找下一个』也配 ⌘C」，预期是新表报红。实际输出：菜单体检 `问题 0`，
而逐条核对那一节报 `✗ 「查找下一个」组合键不对`。查下去发现 **AppKit 在挂上
菜单栏时会自己处理重复键**：那个 item 的 `keyEquivalent` 被清成了空串；
换「最小化」配 ⌘C，它被改回标准的 ⌘M（标准 selector 的键归系统管）。
也就是说"跨菜单撞车"这个状态在能读到的时候已经不存在了 ——
一条按构造永远不会变红的检查，比没有检查更糟（它会让人以为查过了）。
删掉，判据留在"逐条核对意图"那种写法上，代码注释记下了为什么。

顺带修的两条，都是"检查自己"层面的：

- **无障碍判据会误报。** 查找条那两个系统输入框 `stringValue` 是空的，
  被 `空 = 缺名字` 判成缺陷（`需要名字的控件 16　缺名字 2　✗`）。
  但 VoiceOver 念的是 placeholder。判据改成 `空且没 placeholder` 才算缺，
  并加了一对正反探针（空框要被抓、有提示的空框要放过），判据本身抽成
  `needsAccessibleName` 让探针和真检查共用一份，不各写一遍。
- **语言声明。** 查找条一度显示 `Find / Done / Replace`。真原因是**跑的是
  `.build/debug` 那个裸二进制**：没有 bundle、没有开发区域，AppKit 只能退回英文。
  装机版本来就是中文 —— 又一次没遵守"看真实状态要从 `/Applications` 里跑"，
  结论就反了。仍然补上了 `zh-Hans.lproj` / `en.lproj`，但理由换了：没有 `.lproj`
  时 AppKit 一律按 `CFBundleDevelopmentRegion` 出字，**英文用户会被硬塞一套中文边栏**。
  断言落在用户看得见的东西上（查找条那排字），bundle 声明只当背景信息打印 ——
  对照证明那个 plist 键单独在不在都不改变结果，拿它下判决会误报。
  裸二进制下直接给 `未验到`，不给 ✓ 也不给 ✗。

这一轮的对照里还有一次"对照根本没落地"：`mv zh-Hans.lproj /tmp/lproj-hold/`
因为目标目录已存在而失败，`2>/dev/null` 把报错吞了，于是我一度得出"那个 plist 键
才是关键"的错误结论。教训写进了注释和自检里：**对照跑完要确认改动真的在文件里**
（现在都用 `assert` 卡住，替换没命中就直接停）。

### 「点了没反应」也算 bug：六个系统打开调用点一起改

菜单栏的「最近截图」「打开保存目录」、就地预览右键的「打开 / 在访达中显示」、
设置里的「打开文件夹」、以及两处「跳去系统设置」—— **六个 `NSWorkspace` 调用点
原先全都不看返回值**。`open` 失败是静默的：菜单点了什么也没发生，用户只会以为
自己没点到，再点一次。这跟前面几轮修的"把失败说成成功"是同一枚硬币的两面。

统一走 `SystemOpen`：

- 文件"已经不在了"和"在但打不开"分开说（下一步动作不一样：前者去回收站找，
  后者查默认 app / 磁盘还挂没挂着），两句都带上具体目录 —— 只给文件名不知道是哪一份。
- **失败时不要把界面收掉。** 就地预览的「打开」原先无条件 `dismiss(keep: true)`，
  于是最坏情况是"面板没了、图也没打开"，用户连再点一次的入口都没了。
- 「在访达中显示」用的 `activateFileViewerSelecting` **连返回值都没有**，
  所以那条路径上先查文件在不在 —— 而那恰好是它唯一现实的失败。
- 系统设置那两个候选 URL 全试完才说话（中间那次失败告诉用户毫无意义）。
  这一类原先是最不该静默的：点「点此修复」没反应的人，本来就卡在权限那一步上。

顺带修一个只影响观感不报错的漏：「最近截图」每次弹开都按 `fileExists` 过滤**显示**，
但从不回写 —— 死链一直占着那 10 个格子。用户清过一轮截图目录之后，菜单里就只剩
两三条"最近"了，明明截了十张。现在先清账再建菜单，且**没东西可摘时不碰偏好**
（每次点开菜单都写一遍 UserDefaults 是没必要的抖动）。

断言 18 组 10 行，四条反向对照各打红自己那几行：话术合并成一句 → 第 1 行 `✗`；
说明里去掉目录 → 第 3 行 `✗`；把「已打开」塞进失败话术 → 第 4 行 `✗`；
清理改成按名字排 → 保序 + 全活两行 `✗`；判据写反 → 三行 `✗`。

其中两条是**检查自己被写坏**才发现的：
- 第 4 行原本只查 `title` 里有没有「已打开」、`detail` 里有没有「成功」——
  把「已打开」塞进 `detail` 它照样绿。改成两个字段都查全部禁词。
- 保序那条的样本用的是 `a.jpg, b.jpg, c.jpg` —— 本来就已排好，
  `sorted()` 和原顺序给出一模一样的结果，那条断言**永远不会红**。
  换成"插入顺序 ≠ 字典序"的清单（`c, a, b`）之后才真的能分对错。

还有一处流程失误值得记：这一轮的对照脚本一开始把三条对照串在一个 `bash` 里跑，
其中一条的补丁编译失败，脚本却继续往下读**上一版二进制**的输出，
于是"检查不够尖"的结论是假的。现在每条对照都单独确认三件事：
补丁命中（`grep` 数一下）、`Build complete`、然后才读结果。

### 改过的识别文字不再被悄悄丢掉

识别框是**可编辑**的（OCR 认错字要能改），但 `load()` 一进来就把
`textView.string = ""`，而关面板、⌘W、Esc、红按钮、以及"面板开着又截了一张"
这五条路全都不问一句。用户手改过的标点、断行、纠错，会在下一次截图那一刻消失。

现在这五条路都过一道 `confirmDiscardingEdits`：

- 只有**内容和程序写入的基线不一致**才问 —— 识别完直接关掉、什么也没改就关掉，
  一次都不该被打扰。基线由 `setResultText` 统一维护（赋值和基线一起更新），
  三处程序性写入都走它，漏一处就会变成"每次关面板都被问"。
- 问句里点名要存的那个文件（`Grabi-xxx.txt`），默认按钮就是「保存为 .txt 并关闭」，
  复用已有的旁车机制和「保存识别文本」那条设置。
- **图还没落盘时不摆「保存」按钮** —— 点了什么也不会存，那比没有按钮更糟；
  这时说明里直接讲清楚为什么没有（"这张图还没存过，没有可以贴着放 .txt 的地方"）。
- 选了保存却写不出去：说原因、给路径，并且**不关窗** —— 已经关掉的窗口没法补救。
- 「取消」永远是最后一个按钮，所以按倒数第几个判，不按写死的序号 ——
  有没有"保存"项会让序号整体错位。

自检这边有一条**保护自检自己**的断言：填进识别框的测试文本必须不算"用户改动"。
它要是算，`performClose` 就会在离屏渲染里弹一个没人能点的模态框，整套自检卡死。
所以这一行在关窗动作**之前**就打印，且脏的时候跳过关窗那几行而不是继续往下走 ——
一个挂住的自检比一条红字更难查。反向对照（让 `setResultText` 忘了同步基线）实测给出：

```
      ✗ 自检填的文本不算用户改动　→ 会弹模态询问，跳过关窗那几行
      ✗ 第二次 Esc 关掉面板
自检退出码=0        ← 没有卡住
```

另外把自检输出的分组标题统一了：前 17 组是描述式标题，我上一轮加的两组写成了
`── 18)` `── 19)` 编号式 —— 同一份诊断输出里两套风格，读的人会怀疑自己漏看了什么。
全部改回描述式，README 里的组数也跟着改成 19。

`--diagnose` 里的显示器段可以直接验证分辨率：

```
NSScreen 1440×900 pt @2.0x  → 预期截图 2880×1800 px
```

### 主菜单里终于有「截图」了

一个截图工具，顶部菜单里却没有截图命令 —— 这事是这轮翻菜单时撞见的：`MainMenu.swift`
给了 应用 / 编辑 / 窗口 三排，`⌘C`、`⌘F`、`⌘,` 都在，唯独没有"开始截图"。
菜单栏应用不激活时看不到这排菜单，所以一直没暴露；而一旦激活（打开设置、弹权限说明），
这排菜单就是用户唯一**看得见**的入口 —— 全局热键没人会去猜，菜单栏图标又可以被隐藏。

两条命令走的是和全局热键**同一个入口**（`coordinator.handleCapture(silent:)`），
所以权限缺失、忙时忽略、预览与角标这些行为不会分叉。组合键从设置里读，不写死；
`HotKeySpec.menuKeyEquivalent` 把 Carbon 的位掩码翻成 Cocoa 的 flag，并且**只给得出
单个字符的键**：↩、⎋、方向键在 AppKit 里走私有码位，硬塞一个 "↩" 只会让菜单上
显示着快捷键而按下去什么都不派发 —— 那种假象比不显示更糟，所以给 nil，菜单照样能点。

热键可以在设置里改，菜单不能停在旧的一套上，所以应用子菜单挂了 delegate 在弹出前重标。
这一条的验法绕了一步：

```swift
// 把键位故意改歪，再让 delegate 重标一遍，必须按当前设置掰回来
first.keyEquivalent = "q"
app.delegate?.menuNeedsUpdate?(app)
```

不去动偏好本身（自检不该改用户的热键），而"歪了能掰回来"同时证明了两件事：delegate
真在跑、且它读的是设置而不是建菜单时的快照。**`NSMenu.update()` 不会叫到 delegate** ——
第一版用 `update()`，干净树上就红了一行，是自检自己写错，不是产品有问题。

对照：不挂 delegate → 两行红（挂了但不重标 → 一行红；`annotate` 不写键位 → 三行红。

### 「已复制」这三个字得有据可依

截图角标上那句 `　·　已复制` 读的是 `autoCopyImage` 这个**意愿**开关；就地
预览里那句「已复制 N 个字符」则是写完直接就说 —— 而写剪贴板的三个返回值全被丢掉了：
`clearContents()` 返回的是新的 changeCount（**失败给 0**）、`declareTypes` 在这套 SDK
上返回 Int（文档写的是 Bool）、`setString` / `setData` 返回 Bool。

剪贴板写失败不是"没反应"，而是**按 ⌘V 粘出上一份内容**：用户以为复制成功了,拿走的却是
别的东西。所以统一成一个 `Support/PasteboardWrite.swift`：写完必须回读。

```swift
static func verifyText(_ text: String, on pasteboard: NSPasteboard,
                       changedFrom before: Int) -> Bool {
    pasteboard.changeCount != before && pasteboard.string(forType: .string) == text
}
```

图片不整份读回来比对（一张 6K 截图的 TIFF 上百 MB），只查这份剪贴板里到底有没有一个
可粘的图像类型（`availableType(from:)`）。措辞全走纯函数，四个调用点只在回读通过时
说「已复制」，失败时说的是「剪贴板没收下这 N 个字符　·　可能被别的 app 占着，再按一次」
（角标那边拆成标题 + 详情两行，标题短到不会被裁 —— 宽度表里那两行就是从这两个纯函数
取的，不是另抄一份）。

断言跑在**自己的命名剪贴板**（`com.momoxiao.grabi.selftest`）上：自检不该把用户刚
复制的东西顶掉，而命名剪贴板是真·AppKit 机制,不是假对象。回读的三条各钉住一半：
内容被清掉、内容差一个字、changeCount 没动。

| 反向对照 | 结果 |
|---|---|
| 内容比对退化成「有东西就算」 | `✗ 内容差一个字算失败` |
| 回读整个不查（直接返回 true） | 三条回读行**全红** |
| 失败措辞里混进「已复制」 | `✗ 失败那句不出现「已复制」三个字` |
| 没有图可写时也照样 clearContents | `✗ 没有图可写时不动用户原来的内容` |

最后那条是这一轮里被对照**改写法**的一条。它原本只查 `writeImage(nil, nil)` 的返回值,
而那个 false 是回读那一半顺手给的 —— 把前面的 nil 判断整行删掉,它照样 ✓。真正要保护的
是"别为了报失败先把用户剪贴板擦了",所以断言改成回读原内容还在不在,那一刀才落下见红。
中间还有一次更典型的坑：另一处对照的补丁让编译失败了,而 `runpb` 照样打出一行 `✗` ——
那是**上一个二进制**的输出。对照脚本现在都先看 `Build complete` 再吃输出。

### 快捷键录制不再收下「按了没反应」和「抢走全局 ⌘C」的组合

这一轮是从一次实测开始的，不是从猜开始的：`RegisterEventHotKey` 到底会不会告诉
我们"这条快捷键已经被占了"？探针跑出来的答案（前两条是菜单栏里那个正在运行的
Grabi 此刻真实持有的组合）：

```
⇧⌘X  (Grabi 正持有) -> status=0  ref=YES
⌃⌥S  (Grabi 正持有) -> status=0  ref=YES
⌃⌥A  (没人用的对照)     -> status=0  ref=YES
same-process dup       -> first=0 second=-9878
```

**"注册成功"这条路拦不住任何事故**，而两个方向的事故都是真的：

- 往轻了说，用户录到 `⇧⌘4`（macOS 自带截图那四条之一），设置框里显示得好好的，
  按键却不一定轮到 Grabi —— 症状是"按了没反应"，而系统一声不响。
- 往重了说，`⌘C` 同样"注册成功"。全局热键的定义就是**它先于前台 app 拿到按键**
  （Grabi 的 ⌃⌥A 能在任何 app 里生效靠的就是这件事），所以挂上 ⌘C 等于
  把所有 app 的复制抢走。这种故障没有报错、没有日志，用户只会怀疑机器坏了。

于是录制控件在收下之前自己判，分三档：

| 按出来的组合 | 反应 |
|---|---|
| 一个修饰键都没有 | 框里写「至少加一个修饰键」，**继续收键** |
| 只有一个修饰键（⌘C / ⌃A / ⌥3） | 框里写「再加一个修饰键（如 ⌃⌥）」，继续收键 |
| `⇧⌘3 / 4 / 5 / 6`（系统截图那四条） | 先问一句：默认「换一个组合」，坚持就给他 |
| 其余 | 直接收下 |

第三档不硬拦是有道理的：把系统截图换成 Grabi 恰恰是很多人想要的，替用户做主
不合理；但默默收下、让他以为换好了也不诚实。所以问的话里说清楚去哪儿关系统那条
（「系统设置 › 键盘 › 键盘快捷键 › 屏幕快照」），并且**默认按钮必须是安全的那个** ——
回车按错一次就把截图快捷键悄悄换掉了。

同一批实测顺手推翻了两处旧文案：

- `--diagnose` 那行原先印「热键占用检测 / 可用 ✓」。那个 ✓ 是假的：跨进程占用
  它读不出来。现在写「可注册 ✓（仍可能被别的 app 抢着）」，并给撞系统的组合单独标 ⚠。
- 注册失败弹窗原先写「以下快捷键可能已被其他应用占用」—— 真被别的 app 占用时
  根本走不到这个弹窗。现在说的是：走到这里意味着组合键本身不合用；"被别的 app
  占了"是另一种情况（按了没反应），那条路也给了去处。

断言分两半，一半纯函数（`--logic-selftest` 里那一组，24 行），一半真事件
（`--ui-render` 里对着游离的录制控件喂 `keyDown`）：

```
    快捷键录制框
      ✓ 按 ⌘C 被拦在框里：值没变、还在收键、框里写了原因 →「再加一个修饰键（如 ⌃⌥）」
      ✓ 拦完不用重新点：接着按 ⌃⌥A 就收下了（⌃⌥A）
      ✓ ⇧⌘4 不在这里拦（那是「先问一句」那一档，拦重了就是替用户做主）
      ✓ 那台询问的默认按钮是安全的一个（回车 = 「换一个组合」，不是「仍要用 ⇧⌘4」）
```

反向对照一次一刀，八刀各打中该打的那行：

| 改回去的东西 | 结果 |
|---|---|
| 录制路径里短路掉那次判断 | 渲染两行 `✗`，纯函数那 24 行**全绿** |
| 撞系统改成"含 ⌘⇧ 就行" | `✗ 差一个修饰键就不算` |
| 数字键那一半不判 | `✗ 数字键以外的 ⇧⌘ 不算` |
| 阈值从 `<2` 改成 `<3`（拦过头） | `✗ 默认的 ⌃⌥A 不受影响`、`✗ 两个修饰键就放行`、`✗ ⇧⌘4 不在这里拦` |
| 询问框两个按钮换顺序 | `✗ 默认按钮是安全的一个` |
| 决策里把系统判断挪到"撞另一条"之前 | `✗ 撞了 Grabi 另一条时先说「已被占用」` |
| 面板说明写成 `⌘⇧3` | `✗ 一字不差`、`✗ 没有反着写的 ⌘⇧` |
| `displayString` 把 ⌘ 排到 ⇧ 前面 | `✗ 界面写法按 Apple 的修饰键顺序`、`✗ 一字不差` |

第一行那刀最值钱：函数单测全绿、真实路径两行红 —— 老毛病「函数写对了、没人调用
它」在这儿照样会溜过去，所以判断和接线分开钉。最后两刀是同一件事的两头：框里显示
`⇧⌘4`（Apple 的 ⌃⌥⇧⌘ 顺序），说明文字一开始写成 `⌘⇧4`，用户会以为是两条不同的键；
现在说明里那四条由 `displayString` 生成，写反就红。

### 修饰键顺序的守卫从「一个常量」扩到「所有说明文案」

上一轮那条断言长这样：`!hotKeyHelpText.contains("⌘⇧")`。它守住了快捷键面板那一栏，
而**隔壁三栏同样在讲快捷键，一条都没被看**。扩开的契机是先扫了一遍自己这轮写过的
字（我打 ⌥ 会漏，前面已经补过三次），结果 README 自己也中了两处，其中一处就在那段
"探针跑出来的答案"里 —— 顶着逐字引用的格式，写的却是 `⌘⇧X`（正字是 `⇧⌘X`）。

判断做成纯函数 `HotKeySpec.modifierOrderViolation(in:)`：⌃⌥⇧⌘ 四个必须严格递增
（`⌘⌘` 这种重复同样算反），而**只有连在一起**的修饰键才成一串，所以
`⇧ 锁正方形，⌥ 从中心向外扩` 不会被误伤。它对着 9 处文案跑：快捷键说明、截图时的
说明三栏、`--help` 清单、撞系统截图那台询问的四段、录制框里的显示文案、单修饰键的
拒绝理由。装机版实测：

```
  ✓ 把它倒过来写（⌘⇧4）确实会被查出来 →「⌘⇧」
  ✓ 设置 › 截图时的说明 3：顺序对
  ✓ 一共查了 9 处文案，其中 7 处带多修饰键组合（少于 7 处或有文案被改回内联硬编码，这行就红）
      ✓ 说明文案是真贴在窗上的（窗口里读到 80 段文字，其中 4/4 栏对得上；对不上就是自检在查一份没人看的副本）
```

「截图时的操作」那一栏因此从内联字面量抽成了 `SettingsWindowController.captureHelpTexts`
—— 而"抽成常量"正是新的坑：自检可以只读常量，面板改回硬编码也照样全绿。所以
`--ui-render` 加了一条走**真窗口**的接线断言（`paneStringsForSelfTest()` 遍历四个面板
收 `stringValue`）。

对照（一次一刀）：

| 改回去的东西 | 结果 |
|---|---|
| 判断函数废掉（`increasing` 写死 true） | `✗ 倒过来写没查出来`、`✗ 重复的 ⌘⌘` |
| 真文案里把 `⇧⌘R` 写成 `⌘⇧R` | `✗ 设置 › 截图时的说明 3：⌘⇧ 写反了` |
| 整栏说明清空 | `✗ 一个修饰键都没有，这条查等于没查` |
| **面板改回内联硬编码**（常量原样留着） | 逻辑自检**全绿**，只有 `✗ 1/4 栏对得上` 红 |
| 清单少查两处 | `✗ 一共查了 6 处文案` 总数门红 |

第四刀就是接线断言存在的全部理由：它证明自检读的那份就是用户看到的那份。

顺手清掉的：README 里那两处反法、六处源码注释里同样的反法，以及被新守卫彻底取代的
那条 `!contains("⌘⇧")` —— 它只认 cmd 写在 shift 前面这一种反法，另外 11 种照旧放行，
留着还和新尺子成了两把。

**这一轮真正的收获是两处自检脚本自己的 bug。**头三条对照（清空 / 内联 / 缩水）第一遍
全报 `red 0/MISMATCH`，看着像断言没牙 —— 实际是我的分组匹配器只认 `── ` 开头的段落
标题，而 `--ui-render` 的行不在那个结构里，整段输出被筛成空，红行永远数不到；另一条
是我自己把阈值算错了（少查一处不会跌破 7）。教训还是那句：对照报 0 红时先怀疑尺子，
别急着宣布被测代码有问题，也别急着宣布它没牙。

### 「恢复默认快捷键」终于先问一句了

这是个一直没人碰的按钮：它把用户自己录的两个**全局**热键成对丢掉，重注册一遍，
然后一句反馈都不给 —— 而同一个面板上「撞系统截图」那条路都知道先问一句。
判断抽成纯函数 `resetDecision`，三种状态分开：

| 当前状态 | 反应 |
|---|---|
| 两条都还是默认 | **连问都不问**，状态行写「本来就是默认组合（⌃⌥A / ⌃⌥S），没改任何东西」 |
| 有一条不是 | 问一句，只列**真被改动**的那条：`· 截图：⇧⌘X → ⌃⌥A` |
| 答「取消」 | 一个字节都不写，也不重新注册全局热键 |

问句的默认按钮是「取消」—— 这条规矩和系统截图那台询问一样：回车误碰一次不该
把用户选的键换掉。「已恢复」那行只报真改过的组合（静默本来就等于默认时不提它），
延续的是「提示只说真做过的事」那条线。顺带把默认组合收成一份常量
（`HotKeySpec.defaultCapture/defaultSilent`）：原先「读不到时的回退」和「恢复默认」
各写了一遍字面量，两处一旦分家，按「恢复默认」拿到的就不是首启那对键。

自检这边，**对照自己把最大的洞照出来了**。第一版的接线断言是
`button.action == #selector(resetHotKeys)`，看着像钉死了；一对照（把方法体改回
"无条件恢复"）全场全绿 —— 因为它调的是**方法**，不是**按钮**。补成
`clickResetButtonForSelfTest`：用 `NSApp.sendAction` 真派发一次，再把三件事钉在一起
（问了几次 / 写盘几次 / 有没有去重注册）。第二版仍然没红，因为无条件那条路绕开
注入的 write 直接写 `SettingsStore`，而 dev 版此刻两条本来就是默认，写了也等于没写；
最后靠"通知次数"和"先把状态行抹成一个不可能的值"两只手才抓住它：

顺带挖出一条**真的**无障碍缺口：为了让接线断言走真路径，自检这回会按 ⌘1…⌘4 把四个
面板挨个挂进窗口，于是朗读名审计第一次看见了另外三个面板里的控件 —— 需要名字的数量
从 14 跳到 26，其中 4 个没有名字，正好是每个面板的状态行（`label("")` 起步）。
它们平时是空的，只在说"没写成功""按了取消"那种话时才有内容，也就是这套界面里唯一
会报告失败的地方，而读屏用户连它们存在都不知道。四处都补上了显式朗读名（走
`statusLabel(_:)` 工厂，名字和面板一起写死，漏一处就少一个控件被命名）。

### 无障碍清单不再是一张会漏人的手写名单

把朗读名总数摊到**各个面**上打印之后，立刻看见预览面板那一行是 `需要 0`。可预览面板
的主画布是自绘的、吃鼠标的 `ImagePreviewView`（自绘 + 十字光标），它压根不在判据的
类名清单里，所以从来没被查过，也**确实没有朗读名** —— VoiceOver 用户在唯一能查看
截图的那块画布上什么都听不到。补上名字（`.image` 角色），总数 26 → 27。

清单是手写的，手写的清单会两头坏，所以两头都加了闸门：

| 情况 | 现在会怎样 |
|---|---|
| 新加自绘视图没登记 | `✗ 出现了没登记的自绘视图类：X` |
| 登记了却这一趟一个都没见到（僵尸条目） | `△ 清单里这些类这一趟一个都没见到：X` |
| 类名判据本身判错 | 判"是不是我们写的"用**定义所在的 bundle**，不用名字前缀 —— 可执行文件里 `type(of:)` 打出来就是裸类名，第一版因此一个都没匹配上，整条闸门形同虚设 |

闸门一上线又揪出两个没登记的名字（`ToolbarButton`、`PassthroughImageView`），一个都不
是缺陷：前者是 `NSButton` 子类，走"图标 + 空标题"那条判据且都设了名字；后者
`hitTest` 直接返回 `nil`，鼠标根本到不了它。豁免名单里每一行都写着它归谁管 ——
这张表的存在意义是让闸门只对**真正没人管**的名字报警，不是为了让自检闭嘴。

四条对照：

| 改回去的东西 | 结果 |
|---|---|
| 去掉画布的朗读名 | `✗ 需要名字的控件 27　缺名字 1`、`· preview 需要 1　缺 1` |
| 把类从判据清单里删掉 | 总数那行变成 `17　缺名字 0 ✓`（**看着更绿**），新面孔闸门红 |
| 从豁免名单里删一条真豁免 | 闸门红，报出那个类 |
| 清单里塞一个不存在的类 | `△ …一个都没见到：NoSuchViewAnymore` |

第二行是这一轮最想要的证据：漏登记不会让检查变红，只会让分母悄悄变小 —— 没有这道
闸门，"缺名字 0" 完全可以靠"少查一个控件"拿到。

### 清单里四个"面"其实是同一个对象

接着上面那条查：把每个面的分母摊开打印之后，四个设置面板各自报的数**一模一样**
（都是 `需要 3`），而快捷键录制框明明只存在于其中一个面板里 —— 它却出现在四个面上。
原因在收清单的那一行：

```swift
accessibilityRoots.append(("settings-\(name)", content))   // content = window.contentView
```

四个条目登记的是**同一个对象**。清单是留着事后一起遍历的，而遍历那一刻窗口里只挂着
最后那个面板，所以：一个面的控件被数了四遍（分母虚高到 27），另外三个面一个控件都没
被走到。`printPaneFit` / 布局越界那些没中招，因为它们是在循环里当场算的 —— 只有
"先攒着、回头再遍历"的这种会踩。

改成收各面板自己的视图树（`paneViewForSelfTest(index)`），并加一道按
`ObjectIdentifier` 去重的闸门：

```
    ✗ 清单里有 3 个根是同一个对象被重复登记的（数出来的分母是假的，而真正没登记的那面永远查不到）
```

真实分母从 27 掉回 **18**，`缺名字 0` 仍然成立。对照两刀：把根退回 `content` → 闸门红；
让 `paneViewForSelfTest` 取不到视图而静默退回 → 同样红（退回那条路也算漏登记）。

顺带把这条经验用在下一次查数上：**任何"总数"都应该能摊成一张每个面一行的表**，
摊开之后如果几行数字相同得可疑，或者某一行明明是 0 而那块界面一眼就有相关控件，
那就是清单在骗人。

### 覆盖范围改成"真走过哪些面"，不再手写

布局越界那一节原先固定打印一句手写的账：「检查过的面板：设置 4 个 + 预览面板
（默认 / 最小尺寸）」。把账改成从实际遍历里读之后，它立刻和自己的说法对不上了 ——
扫过的只有 `preview@minSize`，**默认尺寸的预览面板从来没被越界检查走过**，而那才是
用户最常看到的样子。补上这一趟，报出来 `0 个控件越界`（这次是真没问题，不是没查），
清单从 5 个面变成 6 个。

```
    检查过的面 6 个（深色 6　·　浅色 6）：preview@default、preview@minSize、settings-hotkey、…
    ✓ 深浅两遍走的是同一批面
    ✓ 0 个控件越界
```

同一节还加了一道**深浅两遍必须走同一批面**的断言。这套自检在这儿栽过一次：预览面板
最小尺寸那张起初被放在 `guard emitChecks` 后面，浅色通道根本没画它，"深浅各一遍"的账
当场就不对（25 张 vs 24 张）—— 现在这件事由断言盯着，不靠人记得。

| 改回去的东西 | 结果 |
|---|---|
| 浅色那一遍漏记一个面 | `✗ 两套外观走的面不一样：只在深色 preview@default` |
| 默认尺寸的面板里塞一个明知越界的视图 | `✗ 深色 1 处 / 浅色 1 处 → …默认尺寸探针 越出 NSView（-30,4–10,10 vs 0,0–1000,660）` |
| 把越界检测器改成永远返回空 | 总数那行照样 `✓ 0 个控件越界`，但 `✗ 自检探针…检测器瞎了`、退出码 1 |

第三行是这一节最要紧的一刀：**"0 处越界"本身不能当证据**，所以检测器自带一个
"故意摆一个坏视图进去"的探针，检测器一瞎探针就红。反过来，我头一版对照写的是
"把探针结果写死成 true"，全场全绿 —— 那测的是变量怎么流，不是检测器有没有牙；
方向错了，重做才对。


### 出图清点：想画的、写成的、盘上真有的，三本账对一遍

`26 个组件 × 2 = 52 张` 这句一直是我手数的。而 `saveInPlace` 画不出来时返回 `nil`
（尺寸算成 0、拿不到 bitmap rep 都会），而 **8 个调用点里 3 个连返回值都没接**，
接了的那 5 个也只是"有就用来对账、没有就悄悄跳过那一段"，没有一个把"这张没画出来"
报成失败；写盘用的还是 `try?`；另一个出口 `save(...)` 里两个 `guard … else { return }` 同样静默，唯一的
失败提示 `say("写入失败 …")` 又不带 ✗ —— 少一张图既不进清点也不进退出码。
这套自检已经为此付过一次账：25 张 vs 24 张。

现在每次出图都记 `(通道, 文件名, 成没成)`，收尾拿磁盘对账：

```
── 出图清点（每一张都该真写到盘上）
    深色 26 张　·　浅色 26 张　·　两边同名 26 张
    ✓ 想画的都落盘了，深浅是同一批（26 × 2）
```

对照三刀，各打一条分支：

| 改回去的东西 | 结果 |
|---|---|
| 让某一次画不出来 | `✗ 30 次想画但没成：dark/settings-save.png、…`、退出码 1 |
| 浅色那一遍漏画一个覆盖层状态 | `✗ 深浅两套画的不是同一批：只在深色 overlay-empty.png` |
| 记账说成了、去对一个不存在的目录 | `✗ 账上写成了但盘上没有：dark/editor-minsize.png、…` |

第一刀一次点出 30 张，是因为那个 `guard` 在两张图共用的函数里 —— 正说明以前这类
失败会一次带走一片，而输出里一个字都不会留。

而且返回值被丢掉。这条通道的失效是**没有症状的**：控件弱引用目标、选择器靠字符串拼，
任何一环断了，框里那行字照样换成新组合、也不报错，只有偏好没动、热键从没换过。
现在只剩 `onChange` 一条类型化通道（接不上就编译不过），并补四条断言钉住它：
被拦的那次一个字节都不许交出去（交出去就是偷偷改了设置）、收下时正好交一次、
`Delete` 清空走同一条通道、设置面板里那两个框确实都接上了通道。
控制"面板里忘了接通道"（也就是旧代码的真实状态）跑出来是
`✗ 设置面板里那两个框都真的接上了提交通道`。

顺带把全仓剩下的 `try?` / `_ =` 扫了一遍：`Permissions.ensureScreenRecording` 里
`_ = requestScreenRecording()` 是**诚实**的 —— 它不靠那个返回值下结论，紧接着读回
`hasScreenRecording` 再决定要不要弹说明窗（`CGRequestScreenCaptureAccess` 本来就是异步的）。
`ImageWriter.discard` 里同名 `.txt` 的 `try?` 是**权衡过的**：主图已经移进废纸篓，
旁车挪不动不值得把成功说成失败，这一点写在函数注释上。

框宽从 150 加到 170 是这张表的副产品，但过程值得记：文案宽度表原先是**手抄**的
—— 文案、字号、框宽各抄一份，于是框一改宽表里还写着 150，新的拒收文案压根没进表。
三样改成从真源头取（`boxText` / `hintTextFont` / `intrinsicContentSize`）之后：

```
  快捷键框(录制)　限  158×1 行　实测 137.2　需 1 行　余量  +20.8 ✓
  快捷键框(未设置)　限  158×1 行　实测  99.1　需 1 行　余量  +58.9 ✓
  快捷键框(零修饰键)　限  158×1 行　实测  95.3　需 1 行　余量  +62.7 ✓
  快捷键框(单修饰键)　限  158×1 行　实测 136.8　需 1 行　余量  +21.2 ✓
  快捷键框(已设)　限  158×1 行　实测  30.8　需 1 行　余量 +127.2 ✓
```

录制态那句 137.2pt 在旧的 150 框里只剩 1pt 呼吸。**这一条不是"检查变红"逼出来的，
是读它打印的数字读出来的** —— 只给 ✓/✗ 的检查会放过这种事。

顺手删了一条自己刚加的断言：`被拦之后依然能改成功，不会因为一次拒绝就退出录制`。
第一刀之下它照样给 ✓（⌘C 被收下后，下一次调用会重新进入录制、照样成功），
也就是说它分不清"拦完继续收键"和"根本没拦"；同一个事实上面一行已经钉住了。


最后再记一笔这次踩的坑，因为它比前面所有问题都隐蔽：给 `--help` 加"和真实分派的
参数对账"那一组断言时，`--logic-selftest` **直接段错误退出**（exit 139），而且因为
stdout 还在 8 KB 缓冲区里，输出停在上一组的半句话上 —— 看着像"打印到一半没了"，
实际崩在别处。

原因：那份参数清单是 `main.swift` 的**顶层 `let`**，而自检分支在顶层代码走到那一行
之前就已经 `exit()` 了。从别的文件读那个全局常量 = 读一块没初始化过的内存。改成
`enum CLI { static let knownFlags }` 之后正常（类型上的 `static let` 是懒初始化）。
教训两条：顶层 `let` 不是"常量"，是"跑到那行才有值的变量"；自检要能在崩溃时留下
线索，得靠**分组计数**这类外部观察 —— 这次就是 `grep -c '^── '` 数出 0 组，才发现
问题不是"某一组红"而是"整个跑挂了"。


### 设置窗终于像 macOS 的设置窗：图标分段 + 分组卡片 + 状态分轻重

之前四个面板是「一排文字分段 + 一堆左对齐的小灰字」。结构没坏（离屏自检 0 越界、
无障碍 0 缺名），但它读起来像一张表单而不像一个偏好窗。三处改动：

- **顶部分段控件带上了图标**（folder / text.viewfinder / command / power）。符号名
  写错时 `NSImage(systemSymbolName:)` 静默返回 nil，所以新增的
  `segmentsWithIconForSelfTest` 数的是**控件当前真的挂着几张图**，不是 `panes` 里那个字符串。
- **每一节改成「标题在卡片外、内容在圆角卡片里」**。卡片底用 `SettingsCardView` 自己
  `draw`：写 `layer.backgroundColor` 会在建视图那一刻把动态色冻成固定 RGBA，
  用户切深/浅色之后卡片会一直停在旧外观上（结果面板的图片底色踩过这个坑）。
  节与节之间靠 `pane()` 给每节钉一条 `width == stack.width` 才等宽 ——
  卡片右边缘参差不齐时，「分组」这个信号就没了。
- **运行面板那三行橙色警告拆了轻重**：第一行「当前机制：…」是对现状的陈述（灰），
  只有 `⚠` 开头那几行才是要处理的（橙）。整段刷橙的实际后果是一堵橙墙，
  真正要用户动手的那一行反而被埋在中间。文本一个字没改，只改配色。

新加的这道闸在 `--ui-render` 里：

```
── 设计系统（深色）：分段图标 + 分组卡片
    · 分段带图标 4/4　✓
    · 卡片数　save 2　ocr 2　hotkey 2　runtime 3　✓
    · 深色 卡片底 vs 窗口底 灰度差 0.079　✓ 分组看得出来
    · 浅色 卡片底 vs 窗口底 灰度差 0.091　✓ 分组看得出来
    判据探针：卡片涂成窗口色时灰度差 0.000　✓ 会被抓到
```

对比度是**算**出来的（把半透明卡片色合成到窗口色上再取灰度差），而不是"有没有
`SettingsCardView` 这个视图"：卡片画成和窗口同色时分组等于零，而代码看着一切正常。
深浅两套一次算完，因为这一组只在深色通道跑，跟着通道走的话浅色的对比度永远没人量。

顺手改掉的另外一处：快捷键那两行的录制框现在拉满整行（定宽 170 的框右边留一大片空，
那一行看着像没排完）。

一条值得单独记的坑：`⚠` 那条判据写成 `line.hasPrefix("⚠")` 时**永远返回 false**。
状态文案里那个警告符是 `U+26A0` + 变体选择符 `U+FE0E`，Swift 的标准等价比较认为
带 VS15 的和光一个 `U+26A0` 不相等。加断言之前它已经静默错了整整一轮：那一版所有行
都被涂成灰色，警告色整个丢了。判据现在逐标量走，并留了一条反向对照
（「机制 ⚠ 未启用」这种句中夹一个 ⚠ 的不算问题行）。


### 「截图时的操作」那 12 行从说明书变成图例，顺便把文案覆盖断言改成不惩罚排版

同一栏里两件事：

- **一行一条、一行一个键**，键名（冒号前那截，≤8 字符）加粗提亮，说明留常规灰。
  整段排下来时找「空格是干什么的」是一次扫读，加粗键名之后是一次定位。
  录制框也从"拉宽填满整行"改回**自然宽度靠右贴齐** —— 系统偏好里
  「标题 …… 控件」就是这么排的，一个能录三个组合键的空框看着像输入框坏了。
- 原来那条「说明文案必须真贴在窗上」的断言是**逐个标签**比的
  （`paneStrings.contains(常量)`）。它防的是"常量还在、面板改回内联硬编码"，
  但顺带把"一整段拆成一行一个标签"也判成红 —— 也就是**惩罚排版**。
  现在比的是四段面板文字按视图树顺序拼起来的整串（`paneJoinedTextForSelfTest`）：
  少一个字照样对不上，而拆行、加粗、控行距都不再触发它。

拆行这件事本身归纯函数管：`--logic-selftest` 里新增一组
`legendLine` 断言（键名那截是 semibold、冒号之后是常规、没有冒号的行一字不加粗、
11 个字符的前缀不算键名、加粗不吞字）。

顺带修掉两处只有画出来才看得见的排版事故：`· 按住图片：挪位置　·　拖边框手柄：…`
一行里塞两个键（第二个漏了加粗），以及最长那行折行把「复制文字」劈成两半。


### 设置窗装进滚动视图：窗口放不下那一截时，从前是被裁掉，现在是能滚到

`showPane` 里那行 `min(max(desired, 240), ceiling)` 干了两件事：内容多高窗口就多高（对的），
以及**屏幕不够高时把窗口压矮**（也对）—— 但它顺手把第三件事也定了：压掉的那一截
**既看不见也滚不到**。面板是钉在 `contentHost` 顶边的一块普通视图，没有滚动视图接着。
同一件事有两条路能撞上，都不需要外接显示器：

- 矮屏（1280×720 那档投影仪）：可见区 695，上限 535，而「快捷键」面板排版出来 602；
- 用户自己拖窗口 —— `window.minSize` 是 520×**200**，比四个面板里最矮的还矮一截。
  建窗口时那句注释「不给最小尺寸就会被缩到只剩标题栏」说明这个风险作者知道，
  只是选了个不够用的下限。

现在四个面板住在 `NSScrollView` 里（`drawsBackground = false`、自动隐藏滚动条、
文档宽度跟可见宽度走、底边钉住内容撑出文档高），切面板回到顶部。
`windowHeight(desired:screenVisibleHeight:)` 把那个决定抽成纯函数，
并且**把"压掉多少"原样报出来** —— 以前这个数字根本不存在，也就没人能问"它去哪了"。

三条断言，各挡一种坏法：

```
── 设置窗的高度分配（放不下的是窗口，不该顺带变成看不见的内容）
  ✓ 屏够高就长到内容高，一像素都不裁
  ✓ 720 的屏：窗口压到 560，而压掉的 80 被报成溢出（有人接才允许压）
  ✓ 反向对照：压窗口不再等于丢内容 —— 溢出必须是非 0 且被说出来的
  ✓ 极矮屏也不开成一条缝：窗口下限 320
  ✓ 内容比下限还矮时按下限给，且不算溢出

    · 面板住在滚动视图里　✓
    · 压到 200 高实测：内容 532　可见 130　滚到底够到 532　✓ 溢出的一截还在文档里，能滚到
```

第二条按结构判、第三条真把窗口压矮再滚到底量一遍。为什么要两条：这台 1600 高的屏上
四个面板**都放得下**，只看高度差的话把滚动视图拆掉也不会有半行红；
而只看 `windowHeight` 的算术也不够 —— 它说"压掉 80"，那 80 是被裁没还是留在文档里，
只有压矮一次、滚到底、量它够不够得到才算看见。

顺带一条**检查自己变瞎**的坑：`overflowingViews` 有意不走进 `NSScrollView`
（documentView 比窗口大是设计如此），面板一搬进去，从窗口往下走的越界体检
就一个设置控件都查不到了 —— 数字会漂亮地停在「0 个控件越界」。
所以那趟体检的根改成了面板自己那棵树（`paneViewForSelfTest(index)`）。


### 设置窗的最小宽度改成从面板自己算：手抄的那个 520 比布局需要的还窄 63pt

越界体检从前**只在默认宽度 620 上跑**，而窗口 `minSize.width` 是手抄的 520。
量完发现四个面板里最宽那个按内容需要 551，加左右留白 32 = **583** ——
也就是说用户能把设置窗拖到比布局需要的还窄 63pt，而那一档从来没被画出来看过。

现在 `window.minSize.width` 由 `minimumWidth(paneFittingWidths:)` 从面板自己的
`fittingSize.width` 算出来，和上一节那条高度决定同一个道理：
**写死的常数会漂，从内容读就不会**。`--ui-render` 因此多出四张
`settings-*-minwidth.png`（清点从 26 × 2 变成 **30 × 2 = 60 张**），
越界体检的面从 6 个扩到 10 个。

```
      ✓ 能拖到的最窄宽 583　面板最宽需要 551 + 32 留白 = 583（拖更窄也不会切：窗口不许比这更窄）
      ✓ minSize 是从面板算的、不是手抄的（读到 583）
── 布局越界（控件被父视图切到）
    检查过的面 10 个（深色 10　·　浅色 10）：… settings-hotkey@minWidth …
    ✓ 0 个控件越界
```

两条断言各挡一种坏法：第一条量"最窄那一档够不够宽"（把 583 手改回 520 会让它红 ——
面板需要 583 而窗口只允许 520）；第二条量 `window.minSize` 和**算出来的那个值**
是不是同一个，挡的是"算了一份、另写了一份"这种两处各写一遍的漂移。
实测 583 那一档四个面板没有一个控件被切，文字按 `preferredMaxLayoutWidth` 正常折行。

反向对照真跑了一遍（把 `minSize` 手抄回 520 再跑一次自检）：

```
      ✗ 能拖到的最窄宽 520　面板最宽需要 551 + 32 留白 = 583
      ✗ minSize 是从面板算的、不是手抄的（读到 583）
    ✓ 0 个控件越界
结论：有 2 行没过　·　红 2 行　·　未验到 0 行　·　退出码 1
```

这一刀顺手量出了**越界体检的一个盲区**：窗口被允许拖到比布局需要的还窄时，
它照样报「0 个控件越界」—— 因为标签是折行而不是越界，横向被压这件事
在"控件有没有出界"这把尺子上根本不留痕迹。宽度够不够只能按预算算，
所以第一条断言读的是 `fittingSize` 而不是越界清单。

### 编辑面板：识别期间一改选区，灰掉的三个按钮就没了理由

`runRecognition` 会把状态行写成「正在识别（全文）…」，同时把
「识别全文 / 识别选区 / 裁剪保存」灰掉。但状态行不是只由识别流程写的 ——
用户**按住拖动改选区**也会重画它，而那一画就把「正在识别」顶掉，
按钮**却还是灰的**。于是界面变成"按钮自己死了，理由却没了"，
而这恰好是这一仓库反复在防的那一类（"点了没反应"的兄弟："灰了没说为什么"）。

修法是把状态行拆成"正文 + 识别中的尾巴"：`busyHint` 存着那句，
`statusLine(_:busyHint:)` 负责拼接，选区变化重画时尾巴跟着走，识别结束（`defer`）清掉。

两条断言一起钉，因为只查文字会漏掉另一种坏法（"文字留着但按钮全亮 = 点了没反应"）：

```
      ✓ 识别中改选区，状态行仍带着「正在识别」（读到：…点「裁剪保存」只保留这一块　·　正在识别（全文）…）
      ✓ 那三个按钮此时确实灰着（识别全文=灰　识别选区=灰　裁剪保存=灰）
```

自检走的是 `enterRecognizingForSelfTest` —— 它复用 `runRecognition` 开头那三行赋值，
而不是另写一份状态：为了量一条断言去复制被测逻辑，量的是赝品。
反向对照也跑了：把 `statusLine` 改回"忽略 busyHint"，第一条立刻
`✗（读到：…「识别选区」只识别这一块，点「裁剪保存」只保留这一块）`、退出码 1。

顺带一处命名：OCR 档那个只写「全部」的按钮，和右键菜单里的「复制全部文字」
是同一件事的两个名字，光看按钮也不知道是"复制全部"还是"全选文字" —— 改成
**复制全部**，和菜单对齐。


### 动作名对账：同一个动作在工具栏和右键菜单里不许有两个名字

上一轮那组双名字（工具栏「全部」/ 菜单「复制全部文字」）是**人眼**看出来的。
这类"第二份真相"在本仓库被抓过好几回，每次都靠眼睛，所以这轮把它变成对账。

先把菜单摊成数据：`contextMenuItems(isOCRMode:)` 返回 `(标题, 图标, 动作)` 清单，
`makeContextMenu()` 按它装配（分隔线由装配方按"这一组在讲什么"插 —— 分隔线不是
一个动作，不该进那份要和工具栏对账的清单）。这样对账就不需要活的预览面板，
也不需要"有 url 才建菜单"那个前置条件。

判据取**动词开头一致**而不是字符串相等：菜单那侧常常多一句说明
（「丢弃（移到废纸篓）」），那是补充不是分家。

```
── 动作名对账（同一个动作在工具栏和菜单里不许有两个名字）
    共有动作 3 个　名字对不上 0　✓
    菜单项数 非 OCR 6 / OCR 7　✓ OCR 档恰好多那一条复制全部文字
```

反向对照跑了：把工具栏那个按钮改回「全部」——

```
    共有动作 3 个　名字对不上 1　✗
    · ✗ 菜单「复制全部文字」 vs 工具栏「全部」
结论：有 2 行没过　·　红 2 行　·　未验到 0 行　·　退出码 1
```

两条附带的防自欺：共有动作**少于 3 个就报红**（某一侧根本没摊开时，
"0 处不一致"是假绿）；菜单形状判"OCR 档比非 OCR 档恰好多一条"而不是判绝对条数
—— 绝对数会挡住以后正当加项，而"两档一样多"这种漏项照样抓得到。


### 那四个开关的名字收成一份：菜单曾写「开机自动启动」而设置窗写「登录后自动启动」

同一个开关两个名字，而且**开机和登录根本不是一回事** —— `SMAppService` 登记的是登录项，
用户登录之后才起来。两处各自硬编码一个字符串，改一处忘另一处是必然的。

现在核心名放在 `ToggleTitles`（`launchAtLogin` / `keepAlive` / `hideStatusBarIcon` /
`showResultPanel`），菜单和设置窗都从它拼：设置窗在括号里补一句"它还会顺带干什么"，
那部分属于面板、不属于名字，所以常量只到括号之前。

`--ui-render` 里新增一道对账，**两处都从界面上读**（共用一份常量 ≠ 两边真的都用了它）：
状态栏菜单摊开逐项看标题前缀，设置窗摊开整棵面板文字看那句话在不在。

```
── 开关名对账（同一个开关在菜单栏和设置窗里不许有两个名字）
    共用名字 4 个　两处都在 4　✓
    旧写法「开机自动启动」残留 0　✓
```

反向对照：把菜单那条改回硬编码的「开机自动启动」——

```
    共用名字 4 个　两处都在 3　✗
    · ✗ 「登录后自动启动」不在菜单
    旧写法「开机自动启动」残留 1　✗
结论：有 3 行没过　·　红 3 行　·　退出码 1
```

第二条"旧写法残留"是单独钉的：只判"新名在不在"的话，把**两处一起**改成第三个名字
照样全绿，而用户看到的还是一个和文档、和帮助行都对不上的说法。


### 菜单里那句「置灰」原来是假的：系统弹出前还会再算一遍可用状态

「编辑最近一张截图…」在没有任何可编辑截图时会被置灰 —— 那句 `isEnabled = false`
写在 `menuWillOpen` 里，读代码完全成立。**实测不成立**：`NSMenu.autoenablesItems`
默认开着，菜单显示前系统会按 target/action 重算每一项的可用状态，而 target
没实现 `validateMenuItem:` 时默认答案是"可用"。于是那句话活不过弹出前那一趟，
用户看到的还是"能点、点下去叮一声"——正是当初写那句想消灭的行为。

现在说话的地方换成 `validateMenuItem(_:)`（`StatusBarController` 声明了
`NSMenuItemValidation`），建菜单时那句删掉了 —— 同一个判断留在两处，
迟早又会有一处是假的。

`--ui-render` 新增「菜单状态体检」，走的是和真实弹出相同的两步：委托重建 → `menu.update()`
（系统那一趟校验），然后读**校验之后**的状态。三种最近截图状态都摊开看：

```
── 菜单状态体检（手工置灰能不能活过系统那趟 update()）
    autoenablesItems = on　·　校验前手工置灰，校验后再读一次
    ✓ 按选择器找到的那条标题确实是「编辑最近一张截图…」
    ✓ 无可编辑截图：校验后仍然是灰的（不是「点了叮一声」）
    ✓ 灰着的时候带了说明（toolTip：还没有可编辑的截图）
    △ tooltip 是悬停才画的东西，离屏渲染验不到它真弹得出来；这里只验了内容非空
    ✓ 最近截图全失效 → 子菜单整个不出现，不留一条空壳
    ✓ 有可编辑截图：同一条校验后是可点的
    ✓ 子菜单 1 张图 + 「在访达中显示全部」
    ✓ 失效 + 有效混着：只列真存在的那张，偏好里的账也同步清了（读到 1 条）
    ✓ 其余带动作的条目校验后全可点，没被系统顺手按灰　异常 0 条
    ✓ 四个开关的勾选标记与偏好一致，且活过 update()　不符 0 项
```

反向对照：把 `validateMenuItem` 里那句改成无条件 `return true`（= 回到修复前的行为），
第一档立刻红 —— 说明这条认得那个 bug，不是碰巧绿。

两点值得记下来：
- 这一节把偏好里的最近截图换成"一个不存在的文件 / 一个真文件 / 两者混着"三种状态，
  跑完用 `defer` 还原 —— 自检要能造状态，但不能把用户的账改脏（`addRecentMenu`
  里的清理是真的会写盘的）。

### 状态行改成按像素量，顺手量出真正的那个问题：警示橙在浅色卡片上只有 1.6:1

起因是想给"⚠ 那行才该喊"补一条**像素级**证据：`advisoryAttributed` 的逐行前景色
是纯函数，逻辑自检里判它怎么判都对，而界面上到底是不是两行两色，从前没量过。

第一条量出来的结论是"两行同色，逐行上色被 `textColor` 盖掉了" —— 于是删掉那一句、

错在量的位置：手挑的一块矩形把左边那个 ⚠ 三角图标也框了进去，图标是橙的，
于是"两行都是橙"。改成从视图树上取 `label.frame` 再换算成像素，量到的就是文字本身：
深色下首行暖度 +0、末行 +104，浅色下 +0 / +90 —— 分色一直是好的。

真正把浅色通道量出问题的是接着加的那条：走一遍设置窗的视图树，把每个 `NSTextField`

灰阶是 Apple 定的层级，判 `tertiaryLabelColor` 不合格等于判系统色不合格。


### 工具栏那条浮条压在亮内容上时，强调色只剩 3.3:1：把对比检查从"设置窗"扩到"逐面量像素"

设置窗那条对比检查要给每个面建模"底是什么"，扩到就地预览就麻烦了 —— 那条工具栏是
**浮在刚截下来的图上**的，底取决于用户截了什么。所以这条新的不建模：
控件矩形里出现最多的那个颜色当底，离底最远的那一撮像素当字身
（取最远的 8% 而不是全部差值像素，因为反锯齿会把边缘混向底色，取全部会把字算淡）。
判据和设置窗那条一致：只判**有彩度**的字，灰阶是 Apple 的层级不判。

跑出来 7 处不合格，全在浅色那一遍：

```
    量到 7 面（有彩度的字 8 处、量不到字的矩形 0 处）　低于 4.5:1 的 7 处　最差 busy · 「 丢弃」 3.29:1
    · ✗ normal · 「 识别文字」 只有 3.35:1
    · ✗ normal · 「 丢弃」 只有 3.29:1
    · ✗ ocr · 「 复制」 只有 3.30:1
```

两个原因叠在一起，都不是"颜色选错了"这么简单：
1. 浮条是 `black @ 0.8`。压在亮内容（浅色遍的窗口底就是 236）上，实际底只有
   (47,47,48) —— **控件的可读性取决于它后面那几张像素**，这本身就是设计缺陷。
   改成 `0.92`。
2. 工具栏用了 `controlAccentColor` / `systemRed` / `systemOrange` 这些**动态色**，
   而系统切到浅色模式时它们会解成更深的一档（`#FF383C` vs 深色那遍的 `#FF4245`）——
   一条永远是深色的浮条，不该跟着系统外观换字色。新增 `barInk(_:)`：
   浮条上的动态色一律按深色外观解算。

修完：

```
    量到 7 面（有彩度的字 8 处、量不到字的矩形 0 处）　低于 4.5:1 的 0 处　最差 failure · 「 再试一次」 6.23:1   （深色）
    量到 7 面（有彩度的字 8 处、量不到字的矩形 0 处）　低于 4.5:1 的 0 处　最差 failure · 「 再试一次」 5.40:1   （浅色）
```

反向对照：把 `barInk` 改成原样返回 —— 逐面那条**没有红**（0.92 那一处就够把对比度抬过线）。
所以这条性质不能只靠像素扫：另加一组 `--logic-selftest`「浮条配色」，直接问
"同一个色在两套外观下解出来是不是同一个值"，改回去立刻红两处
（`✗ 丢弃（红）：深浅两遍都是 #FF383C`）。同一组里对默认强调色那行会明说
"这个色两套外观本来同值，这条对它只是不红" —— 一条查不出东西的检查要自己承认这点。

另外两处顺手：
- 按钮的标题单元格自己就是一个 `NSTextField`，同一个字被量了两遍（15 处 → 8 处）。
  走控件树时跳过"里面有文本控件的按钮"。
- `String(format: "%s", 某个 Swift 字符串)` 会让整个 `--ui-render` 直接死掉，
  而外层只看退出码的话这就是"跑完了"。Swift 字符串一律走插值，只有 `%d`/`%.2f`
  这类数值才用 `String(format:)`。


### 自检改成无头：不再往用户屏幕上弹窗

用户反馈：`--ui-render` 一遍几十张图，编辑面板的窗口一次次盖到正在做的事情上。
根子在自检走了真的显示路径 —— `show(image:url:)` 里那两句
`makeKeyAndOrderFront` + `NSApp.activate` 是给"人正在用"的时候写的，
而 `cacheDisplay` 离屏画本来就不需要窗口在屏上。

新增 `Headless`（`main.swift` 里的 `headlessFlags` 决定哪几档进无头）：
激活策略 `.prohibited`、上屏动作走 `Headless.onScreen { }`、
自检构造的菜单栏图标直接 `isVisible = false`。

**但编辑面板那个窗口还是得上屏** —— 查找条 / Esc 那三项查的就是键盘路由，
而 key window 必须是上屏的窗口。改成把它挪到屏幕外面（-20000,-20000），
并给窗口子类 `EditorPanelWindow` 重写 `constrainFrameRect`：
系统默认会把要上屏的窗口**拽回屏幕里**，那一下"拽回来"才是用户看到的弹窗。

然后加了「无头自检的自检」，三条：跑完没有任何窗口落在用户看得见的屏幕上、
策略是 prohibited、菜单栏图标没占格子。这条检查差点是永远绿的假检查 ——
第一版判据用 `occlusionState.contains(.visible)`，反向对照（把窗口故意留在屏内）
**照样绿**：`.prohibited` 的 app 收不到遮挡更新，那个位从来不置。
换成 `isVisible && 和某个屏幕有交集`（再放过 AppKit 自己挂出来的菜单窗那类系统窗）
之后，反向对照立刻红：

```
    ✗ 跑完没有任何窗口在屏上：NSWindow「Grabi — Grabi-selftest.png」@{216, 93}
```

修完：

```
── 无头自检（不给用户的屏幕留东西）
    ✓ 跑完没有任何窗口在屏上
    ✓ 激活策略 prohibited、无头开关是开的（策略=2 开关=true）
    ✓ 自检构造的菜单栏图标没占格子
```

`--logic-selftest` 里另加三条守住闸门本身：无头时上屏动作被跳过、
正常时照常执行（开关不是永远沉默）、跑完把全局开关还原。
`--help` 也写了这一条，用户不用猜自检跑起来会不会有东西冒出来。

⚠️ 一条通用的坑，单独记：**判据要挑"这台机器上真的会变的信号"**。
`occlusionState` 在文档上正是"这块屏上有没有你的窗口"，但在这个配置下它从不置位 ——
只看代码写得多合理是发现不了的，只有给检查做反向对照才发现它是死的。

### 面板缩到最小时，结果栏把看图那一列挤成了配角

结果栏（右边那列"识别结果"）以前是一条写死的 `width == 330`。1000 宽时它占 33%，
一切都好；把面板拖到最小 720 时，**同一条约束**让它占到 46%，而看图那一列只剩
350pt —— 比配角还窄。可这个面板的主活是"在图上框一块"，读结果才是第二步。

这条不是看出来的，是算出来的：`720 − 14 − 12 − 14 − 330 = 350`。固定值在默认尺寸
下永远量不出问题，所以量的是**两档**。

**为什么不用比例约束。** 上一版试过 `width == container.width × 0.4` 加上下限，
面板从 1000 宽开成了 825（`--ui-render` 那行 `editor: 825×660` 就是它）。原因不
是比例本身：那条方程**能反解出容器宽度**，而这一层窗口的开口尺寸恰恰是被内容的
Auto Layout 拟合宽度牵着走的，于是拟合值反过来定了窗口。所以这次把约束**留在
常量**这一形态，只在窗口 resize 之后重算那个常量的值：

```swift
static func resultPanelWidth(containerWidth: CGFloat) -> CGFloat {
    min(max((containerWidth * 0.33).rounded(.down), 240), 330)
}
```

33% 是照着 1000 宽反推的，所以默认档算出来还是 330，**用户最常看到的那一档一格
没动**；往下有 240 兜着（再窄就读不了字了），往上封顶 330（宽屏也不让配角变主角）。
挂钩在两处：`windowDidResize`，以及窗口建好之后立刻对一次 —— `WindowFrameMemory`
可能把窗口恢复成一个比 1000 窄的尺寸，而 `didResize` 不会为"建好后没被拖过"补发。

`--ui-render` 里量真实的两列（第一条对开口尺寸，中间两档对配比，最后两条是对照和回位）：

```
── 编辑面板两列配比（看图 : 结果）
      ✓ 开口尺寸对得上：政策要 1000×660，窗口真开成 1000×660
      ✓ 开口档 容器宽 1000　看图 630 : 结果 330 = 1.91　算式说 330
      ✓ 最小档 容器宽 720　看图 440 : 结果 240 = 1.83　算式说 240
      ✓ 反向对照：结果栏改回旧的固定 330，配比掉到 1.06（判据 1.50）
      ✓ 拖宽再拖窄之后自己回位
```

判据用**两列之比 ≥1.5**而不是百分比：比例直接对着"谁是主角"写，而百分比得先把
边距和列间距从容器宽里减掉 —— 那等于把 `buildContent()` 里的 14 / 12 / 14 抄第二份。
每档还顺带比一次"量到的 == 算式说的那个"，否则 `applyResponsiveResultWidth` 没挂上
也是绿的。

第一条（开口尺寸）是这一轮补上的一道**旧缺口的账**：`editor: 1000×660` 那行一直只是
**印出来给人看**的，825 那次是靠人眼从一行数字里挑出来的。现在它变成断言 ——
政策（`openingSize()`）说该开多大，和窗口真开成多大，对不上就红。

最后那条"回位"是被反向对照逼出来的：先 `forceResultWidthForSelfTest(330)` 绕过算式
把常量按回旧值，再**拖宽一次、拖窄一次**（只设同一个值不会触发 resize，那就什么也
测不到），要求结果栏自己回到算式的值。它钉住的是"让位每次都算，不是算一次就定死"。

`--logic-selftest` 那边把算式本身的形状钉成七条（默认档没动 / 有下限 / 有封顶 /
单调 / 两端配比达标 / 反向对照），快速门不用渲染就能拦住改坏系数。

**三个反向对照都实跑过**（每个都是临时改代码跑一遍再还原）：

| 临时改成 | 结果 |
| --- | --- |
| headless 下短路 `applyResponsiveResultWidth()`（等于旧行为） | 红 2 行，报的正是旧的 `350 : 330 = 1.06`、`46%` |
| 只留裸比例 `width == container.width × 0.4` | 红 3 行（量到 400 / 528，算式说 330 / 240） |
| 比例 + 上下限（**当年那版尝试的原样**） | 开口那条红：`政策要 1000×660，窗口真开成 466×660` |

第三行是补这条断言的理由：拟合宽度反噬窗口尺寸这件事，现在闸门自己看得见，
不用等人去读一行打印。（当年那版报的是 825，这次复现出 466 —— 数字取决于当时
配的下限，坏法是同一个。）

顺带记一个坑：**给一条 multiplier 约束改 `.constant` 不是设宽度，是加偏移**。
第二个对照里 528 = 720×0.4 + 240 就是这么来的 —— `applyResponsiveResultWidth`
假定自己手里那条是常量约束，这个假定现在由"量到的 == 算式的值"那条判据守着。

### 编辑面板能缩放了：以前在 2880 宽的截图上框一小块，是凭感觉


大图是这个工具的日常：一张 2880×1620 的截图，塞进 630pt 宽的列里，倍率只有 **0.22**。
而"框一块只识别这一段"恰恰要求看清那一块里有什么。原来 `imageRect` 只有一条算式
（等比居中装下），也就是**根本没有缩放** —— 用户只能在小图上凭感觉拖一个框，
再等一次 Vision 往返才知道框错了。

现在：`⌘=` / `⌘−` 放大缩小、`⌘1` 实际大小、`⌘0` 适合窗口（新增一排「视图」菜单），
放大后两指/滚轮平移，`⌘` 滚轮和双指捏合围绕指针缩放。

三个设计决定值得记下来：

1. **倍率是绝对的，不是相对"适合"的。** `ImageZoom` 只有 `.fit` 和 `.scale(每像素多少点)`
   两档，所以"实际大小"真的是 1 像素对 1 点。如果按"相对适合 ×1.25"来定义，
   2880 宽的图放大 5 次还是糊的，而小图放大 5 次已经飞出天际 —— 同一个手势两种意思。
2. **拖动留给框选。** 平移不抢主手势（那是这个面板的主活），交给滚轮 / 捏合。
3. **左下角一枚倍率徽标**（`300%`），只在非适合档出现。放大之后图被裁掉大半而
   框选手势毫无变化 —— "你现在看到的不是整张图"必须挂在眼前，菜单里写一次不够。

上限 800%（再大只是把像素糊开）。下限跟着"适合"走：大图不许缩得比装下还小；
小图反过来允许回到实际大小，哪怕那比适合窗口还小 —— 这条是 `clampedScale(raw:fit:)`
里那个 `min(fit, 1)`，写死成 1 的话，从 fit 往外缩会**反而把图放大**。

**选区不受影响**：它一直是归一化坐标（0–1，原点左下，和 Vision 一致），缩放改的
只是"怎么画"。但这句话正是一个静默错误的藏身处 —— 往返换算错一次，用户看着框
还在，送进 Vision 的已经是另一块。所以 `--logic-selftest` 新增 11 条把这句话变成
不变式（`编辑面板缩放`）：适合档算的是像素密度、放大后**必须盖住整个视图**
（不许露空白边）、往死里平移夹取之后仍然盖住、选区在三种画法下原样往返、
围着鼠标放大时鼠标底下那个图片点不搬家、上下限和封顶、徽标读数，加一条反向对照
（跳过夹取直接平移 10000，判据当场要看见空白边）。

`--ui-render` 那边量真像素。徽标这一条用的是**一对几何完全相同的图**：
`.fit` 和 `.scale(fitScale)` 画出来的图片矩形是同一个，所以两张图的差集只可能是
徽标 —— 实测差 714 个像素，且外接框严丝合缝落在徽标矩形里。

这条判据上线时立刻抓到两件我没想到的事：

- 位图第 0 行是**顶部**而视图 y 朝上。第一次跑出来差集 x 和徽标 x 完全对上、
  y 正好差 `660 − 60` —— 是量出来的，不是推出来的（README 里那句换算注释就来自这里）。
- 读徽标位置的代码写在了"切回 `.fit`"之后，于是拿到 `nil`，判据拿着空矩形去比 ——
  那是自己把自己骗过去。现在位置**趁徽标还在**的时候取。

「视图」那四条的接线单独判（`target` 留 nil、selector、键、修饰键、
`contentView` 接得住、它自己说该亮，加一条"面板不在时四条必须变灰"的反向对照）。
这里有一个诚实的边界要写清：**无头通道拿不到 key window**（`.prohibited` 的 app
不能激活），而 `NSMenu.update()` 判"能不能点"是从 key window 的响应链往下走的 ——
所以那一步没实测，报成 `△ 未验到`，走的是结构判据（接住者就是窗口的 contentView，
而 contentView 必然在链上）。滚轮/捏合的**方向感**同理只有真机能验，也报 `△`。
`未验到` 从 1 行变 3 行，这是记账变严了，不是变差了。

反向对照还跑了一次"把 `mainMenu.addItem(viewMenuItem())` 删掉"：立刻红
（`✗ 主菜单里没有「视图」`，退出码 1）。

顺手被闸门自己抓到的一件事：新加的 `EditorContainerView` 一出现，无障碍那节就报
`✗ 出现了没登记的自绘视图类` —— 那道口本来就是设计成"新面孔必须显式交代它归谁管"。
登记为"纯容器，只转发菜单动作、不接鼠标、没内容可念"。

### 那根把手交出去：两列的比例改成用户拖，而且它必须真的跟着指针走

上一轮的自动让位解决了"别挤成配角"，但 33% 那个数仍然是**我们替用户定的**。
读长文的人想把结果栏拉宽，框小块的人想把图放到最大 —— 这件事没有正确答案，
只有把手。所以两列之间加了一条可拖的分隔条（双击恢复，「视图」里也加了
「恢复默认比例」），拖出来的比例存在 `editorResultFraction` 里。

**它顺手揭出一个毛病：那条绝对的 330 封顶让把手是假的。** 1000 宽时 33% 恰好等于
330，于是"往左拖（想拉宽结果栏）"一寸都拖不动 —— 一根拖不动的把手比没有把手更让人
火。而 330 当初真正想守的东西是"配角别变成主角"，那是个**比例**。现在直接按比例守：

```swift
static func resultPanelWidth(containerWidth: CGFloat, fraction: Double) -> CGFloat {
    let ceiling = max(240, (containerWidth - columnGutter) / 2.5)   // 看图 ≥ 结果 × 1.5
    return min(max((containerWidth * fraction).rounded(.down), 240), ceiling)
}
```

默认档一格没动（1000 × 33% = 330），但 1600 宽时能拉到 383 —— 宽窗口上真的允许拉宽。
配比那条不变式现在对**任何宽度 × 任何合法比例**都成立（自检里是 5×5 的格子，不是两端抽查）。

`columnGutter` 是从那几个约束常量（`imageLeadingInset + dividerGap + dividerWidth +
dividerGap + resultTrailingInset`）**算出来**的，不是抄的：自检拿它对账
"看图 + 结果 + 这条 = 容器宽"。写死一个数就是第二份真相，而且是一改约束就悄悄失效那种。

**三件实测到的事，都不是推出来的：**

1. **把手会永远比指针偏 6.5pt。** 结果栏的左边界不在指针上，而在指针右边
   「半个把手 + 一条呼吸」那里。第一次跑出来是「指针 700 → 落在 694」。
2. **这个 bug 只有"锚在现实上"的那条判据抓得到。** 逐条比"落点 vs 算式说的落点"
   三条全绿 —— 因为两边用的是**同一条**（写错的）算式。红的是那条
   「至少一处指针和把手严丝合缝」，它比的是指针（现实），不是另一个公式。
   反向对照实跑：把 `fraction()` 里那半个把手减掉，逐条那三条照样 ✓，
   严丝合缝那条立刻红、退出码 1。**自己验自己**长什么样，这就是样子。
3. **把手画得出来是量出来的**：数分隔条那块里有几列像素带墨 —— 只有那条 1pt 的线
   会是 1 列，中间三颗点把它撑到 3 列；同一时刻一块同样大小的纯背景对照是 0 列。
   把点去掉跑一遍：0 列、当场红。（第一版点用 `tertiaryLabelColor`，浅色通道里
   几乎看不见，就是被这个数逼着换成 `secondaryLabelColor` 的。）

`--logic-selftest` 那 15 条里还抓到**自检自己写反**的一条：往**左**拖出界是"想让结果栏
无限宽"，该夹到**上限**；我原本写成夹到下限。判据红得很清楚 —— 而这次红的是判据，
不是产品，所以修的是判据（这正是反向对照存在的意义：它连"检查本身"也检查）。

磁盘上写坏值也兜得住：`editorResultFraction` 读的时候夹进 `[0.22, 0.45]`，
自检直接往 `UserDefaults` 写 `0.99` / `-3` 再读回来验这道门。
（注册默认值那一步不能省：`defaults.double(forKey:)` 对"没设过"给的是 `0.0`，
会被夹成下限 0.22 —— 那样第一次打开面板看到的就是最窄那一档，而不是 33%。）

无障碍那节同步登记了 `ColumnDividerView`（它有朗读名，走的是"需要名字"那一类）。

`dist/` 的 dmg / zip 已按这一版重打（版本号仍 2.0.0）。

### 拖进来就能识字：这个工具原本只有一条入口

编辑面板以前只认一种图 —— **刚截的那一张**。可"我想把手机拍的那张纸、微信里收到的
那张图认一下字"是同一个需求的另一半，现在只能靠"把那张图显示出来再截一次"绕过去。
`grep` 了一下 `registerForDraggedTypes` / `performDragOperation`：**两个方向一个都没有**。

现在可以把图片文件从 Finder 拖到面板的图上。判定、加载、反馈三件事都收在
`Sources/Grabi/UI/ImageDrop.swift` 里，因为"拖进来的是 txt 到底拒不拒、拒了说什么话"
不该等到人手去拖才能知道。

**每一次拒绝都带一句话。** 光标变一下又变回去、别的一概不说，是最让人不确定的一种 ——
用户分不清"这里不能放"和"我手慢了"。所以：拖的时候图上就铺一层染色 + 虚线框 +
正中一颗提示丸（"松手就识别这张图"），拒的时候那句理由写在同一颗丸里；判定放行但
**真读不出来**（扩展名对、内容不是图，或者那是个叫 `x.png` 的文件夹）时同样要说话。
`--logic-selftest` 里有一条就是钉这个的：`[空手, txt, 文件不在了]` 三种拒绝
**每一个都必须带非空理由**。

判定用系统的 `UTType.conforms(to: .image)`，不手写扩展名清单 —— 手抄那份要么漏了
`jpeg` 这种别名，要么在系统哪天认了新格式之后悄悄过期。

**拖进来就直接开始识别整张。** 把图拖进一个识字工具里，意图没有第二种读法；停下来
等用户再点一次「识别全文」，是逼他多做一步他刚刚已经做过的事。一次拖多张只收第一张，
但**忽略了几张要报出来**（挂在 `busyHint` 上 —— 挂别处会被"正在识别"那句顶掉，
而这正是这个面板以前犯过的错，见前面那一节）。

守卫里最值得记的两条：

```
      ✓ 拖入态画出来了：两图差 365617 个像素（整列染了一层色）
      ✓ 反馈没越界：差集 {{14, 44}, {629, 584}} 全在图片那一列 {{14, 44}, {629, 584}} 里
      ✓ 反向对照：收掉拖入态再比一次，差 0 个像素（分毫不差，量到的确实是那层反馈）
```

无头通道造不出真的拖放手势，但**画没画东西**是可以量的：同一份几何、只把拖入态
开关切一下，两张图的差集就是那层反馈。差集还必须**不出图片那一列** —— 把提示画到
结果栏上去是一种走样。反向对照（关掉再比一次 = 0 像素）说明这个数量的确实是反馈，
不是渲染本身在抖。把 `drawDropFeedback` 那一句去掉实跑：差 0 个像素、当场红、退出码 1。

`registeredDragTypes` 这个属性 AppKit **只给写不给读**，所以判"到底登记了没有"不能
靠一个自报家门的布尔量 —— 改成重写 `registerForDraggedTypes(_:)`，把真正递给
AppKit 的那一份记下来再比。没登记的话系统压根不会把拖放送过来，后面所有判定和
绘制都不会跑到，所以这一条排在最前面判。

还有一个自己查出来的漏：判定表只验了"假 png 读不出来"，而**"真 png 读得出来、
尺寸还对"才是拖放真正成事的那一步**。补了一条正向的（写一张 320×200 的真 PNG 到
临时目录 → `ImageDrop.load` → 尺寸必须对）。只测否定面、不测肯定面的判据，
绿起来是一样的，含义却差一截。

另外把 `NSImage(contentsOfFile:) → cgImage(...)` 那条加载从 `ShotCoordinator.editLastShot`
里提出来共用 —— 各写一遍的话，将来一边修了方向/位深问题，另一边不会跟着好。

`--ui-render` 的 ✓ 行数从 151 涨到 157。`dist/` 的 dmg / zip 已按这一版重打。

### 图上一右键，什么也没有

缩放、恢复默认比例、打开文件、复制图片这几个动作这一轮之前**只有顶部菜单栏一个落脚点**。
顶部菜单栏是熟人的地方：新手不知道「视图」里有"适合窗口"，也懒得为一个动作去翻菜单。
而 macOS 用户在画布上唯一会试的那一下就是**右键** —— 那一下落空，这个面板就还是个半成品。

于是画布有了上下文菜单（`EditorPanelController.contextMenuEntries(hasFile:)`）：
识别全文 / 识别选区 · 裁剪保存 / 清除选区 · 放大 / 缩小 / 实际大小 / 适合窗口 / 恢复默认比例 ·
复制图片 / 复制文字，图落过盘再加一组 打开 / 在访达中显示 / 复制文件路径。

三件事是按本仓库的老规矩做的：

**一，菜单和工具栏共用同一个选择器，不写 `menuXxx` 转发壳。** 第一版就是那么写的，
回头一看是十个名字、五份逻辑。同一个动作两个入口名，改了一边另一边还在跑旧路子，
而"名字对账"那种检查恰好抓不出"两个名字其实做同一件事"的分家。现在工具栏那五个动作
的 `button.action` 和菜单条的 `item.action` 是**同一个 selector**，自检读的就是这一条。

**二，可用状态只有一个出处。** `validateMenuItem` 读的和 `refreshActionState()` 那五个
按钮同一批条件（选区、有没有结果、是不是在识别、文件还在不在盘上）。菜单里灰着、
按钮上却亮着（或反过来），用户读到的是"这软件自己不知道自己要干什么"。

**三，快捷键是读来的，不是抄的。** 菜单上显示 `⌘R`、`⌘S`、`⇧⌘C` 这些，
是因为右键是新手唯一会试的地方 —— 键只藏在 tooltip 里就等于没有。但字面量不能抄第二份：
`keyEquivalentForAction(_:)` 从工具栏那几个按钮现读，改了按钮那边菜单不会继续挂着旧键骗人。
「放大 / 恢复默认比例」那几条的键归顶部「视图」菜单，工具栏没有对应按钮，所以菜单里
**不给自己编一个键**。

复制图片复制的是**画布上这一张**（裁过就是裁过的那张），状态行报"已复制图片 640 × 480 px"，
数字就是证据；写剪贴板走的还是"写完回读"那一套，失败时说"剪贴板没收下这张图　·　再按一次"。
「复制文件路径」也一样回读。`SystemOpen.reveal` 发现文件已经被别的窗口删掉时，
状态行写"这张图已经不在这儿了：(完整路径)"，不是"没能打开"。

守卫里两条值得记：

```
      ✓ 两个状态下比了 10 个动作，灰在同一处
      ✓ 文件在盘上时「打开 / 在访达中显示 / 复制文件路径」三条亮着（/tmp/Grabi-selftest.png）
      ✓ 反向对照：文件被别的窗口删掉后那三条自己灰掉，不等人点出错了才说
```

第一条形如"把 `validateMenuItem` 里任何一条改成常量就会红"：拿真改了一版的
`clearSelection` 试跑，当场报「清除选区」在"刚打开"时菜单亮、按钮灰，退出码 1。
第二、三条锚在**盘上的真相**而不是 `url != nil` —— 面板拿着一个已经不存在的路径时，
那三条必须自己灰掉。两头各碰一次是有原因的：只查一头的花法是"文件根本不在、三条一起灰"，
那种灰照样能过"三条都在"这种检查。另外两条反向对照：没接面板的画布必须交不出菜单
（不然"画布交出菜单了"可能只是系统默认那份顶着）；`key: owner.keyEquivalentForAction`
那一转去掉，五条"菜单显示 无键、按钮是 ⌘R"就全报了。

判据本身也错过一次：`NSMenuItem` 新建时 `keyEquivalentModifierMask` **默认就是 ⌘**，
拿"修饰键非空"当"有没有快捷键"一查就红 —— 那是判据写错，不是产品写错，改看键字符。

### 裁剪保存不再吃掉原件：没有撤销的动作不许不可逆

`⌘S`「裁剪保存」原来是**就地覆盖**那个路径上的文件。框选偏三个像素、或者 ⌘S 按错一下，
被裁掉的那半张就永远没了 —— 而这个面板没有撤销，用户也不会先另存一份。
一个不可逆、又没有回头路的动作放在一键盘快捷键上，是这个面板里最贵的一处草率。

现在走的是本 app 已有的「丢弃」语义：**先把原件挪进废纸篓，再在原路径写出裁剪后那一张**
（`ImageWriter.replace(_:at:)`）。挪不动就**整个不做** —— 宁可报"裁剪没保存：原件挪不进
废纸篓（原因）　·　为保住原图，磁盘上什么都没动"，也不能把原件毁掉又装作成了。
状态行三种结局三句话，每一句都说清**原件现在在哪儿**：

```
  ✓ 原件真的挪进了废纸篓，照着报回来的落点**读得回那张 64×64**
  ✓ 原路径换成了裁剪后的 32×32，而 144dpi 还跟着（挪走之后再读就没了）
  ✓ 反向对照：自检挪进去的那一个已删干净，用户的废纸篓里不留测试文件
  ✓ 原件挪不动时**保存整个不做**（不是「覆盖成功」然后把原件丢了）
  ✓ 路径上本来就没有原件：照写，但不谎称「挪进了废纸篓」
```

两个坑是这次自己踩出来的，都写进注释了：

**DPI 必须在挪走之前读。** 上一节刚修过"裁一刀图就凭空大一倍"（覆盖写要带上原文件的 DPI），
而 `replace` 一旦先把原件挪走，`overwrite` 再去那个路径读 DPI 就已经读不到了 ——
照原样接起来会把刚修好的毛病换个名字复活。所以 `overwrite` 多了一个 `dpi:` 参数，
读原件的时机由调用方管，并把"什么时候读"写成了这个函数的注释。

**自检自己也会造垃圾。** 挪废纸篓那半必须在真盘上实跑（只验话术的话，`trashItem`
报回来的落点是假的也照样绿），跑完立刻按那个落点删干净、并**断言删干净了**。
渲染自检那一半本来想验"没原件时不说谎"，却先 `png.write(to: target)` 把原件造了出来 ——
于是它跑的是有原件那半，往用户废纸篓里塞了两个 `shot.png`，判据当场红：
「不谎称『挪进了废纸篓』　读到：原件已挪进废纸篓：shot.png」。红是对的，
错的是自检的前提：**面板要的图本来就在内存里，那个路径不该被预先占住**。
改完之后那条判据里多带一个 `盘上原本有文件=false`，把前提本身也报出来。
（这次留下的那两个文件删不掉：`~/.Trash` 归 TCC 管，shell 列不了也删不了，
用 Finder 脚本又会弹授权窗 —— 请手动清空废纸篓时留意两条 `shot.png`。）

「丢弃」那两条路（`trashItem` 落点、失败必须抛出去）现在和裁剪共用一个
`trash(_:)`：两处各写一遍 `trashItem`，将来一边修了（只读挂载点那个 513）另一边不会跟着好。

### 选区那四颗白点以前拖不动（而放大之后它们会塌成同一个点）

框完一块想微调，以前只有一条路：**重画一遍**。按住已有的白点拖，得到的是一个新的框，
不是把那个角挪一挪。白点是画给眼睛的承诺，手指必须兑现 —— 这和本仓库前面那根
"看着能拖、其实拖不动"的分隔条是同一类毛病，只是这次换了个地方长。

现在四颗白点都能拖：**对角钉住，被拖的角跟到指针**，一路跟着一边广播（状态行的
尺寸数字实时变）。指针跑到图外的留白上会夹在图片范围内（灰边不算进选区）；
**拖过对角就翻正**，不给负宽高、也不钉死不动。光标在四个角上换成左右方向的箭头
（这套 SDK 里 `NSCursor` **没有**斜向 resize 光标，`NSCursor.h` 只有 left/right/
leftRight/up/down/upDown/all —— 不能装作有 ↖↘，那就按主导方向给一支单头箭头）。

只给四个角，不加"边把手"：**画的就是这四个，能拖的也必须正好是这四个**。加一圈
没画出来的把手，判据会说"八个方向都能拖"，而用户看见的只有四个点。
圆心、绘制、光标、抓取四处共用 `handleCenters(of:bounds:)` 同一个函数。

自检把两件本来会蒙过去的事挖了出来：

**① 判据自己可以是空的。** 第一版量"圆心那块有没有那一圈强调色"，四颗全过；
把 `drawHandles` 整句注掉再跑 —— 照样全绿。因为选区那圈 1.5pt 的描边**也过圆心**，
数到的蓝点全是描边。换成"同一个 5×5 圆心在有选区/没选区两张图里的平均亮度差"
之后，注掉那句立刻红四行、退出码 1。顺带发现底图是合成的：左半张纯白、右半张近黑，
白点压在白的地方什么都量不到 —— 所以选区整个挪到暗的那半，并且把"底下确实暗"
这个前提也单独报一条，免得判据哪天静默失效。

**② 缩放后会塌点。** 300% 下按住右上角，`cornerHit` 报回来的是 `upperLeft`：
夹取把跑到视图外的角一律夹到边上，于是两颗点叠进同一个位置，按住它只能靠
遍历顺序猜用户想拖哪个角，猜错就是把左边那条边当右边拖。改成
**看不见的角不画也不抓**（`isInView`，含边界 —— 整张选中时四个角正好压在边上，
用 `NSRect.contains` 会说"一颗都看不见"，那是把老功能判没）。现在 300% 下剩下
0 个角可见就不给点，而每个给出来的点都只对应它自己那个角。

拖老路也没被堵掉：反向对照专门按住**选区正中**拖，必须还是"重新框一块"。
`mouseDown/Dragged/Up` 三步抽成 `beginDrag/extendDrag/endDrag`，自检用
`simulateDragForSelfTest(from:to:)` 喂三个坐标走**同一份实现**（无头通道造不出真的
`NSEvent`，而"验的是另一套逻辑"等于没验）。

`--logic-selftest` 新增 11 条（四颗各自按得住、圆心外 13pt 按不到、扁选区给的是
**最近**的那个角而不是遍历到的第一个、对角钉住、夹在图片范围内、拖过对角翻正、

### 覆盖层以前只认两个键：⏎ 采用候选、方向键一像素微调

候选框跟着鼠标走，可"采用"只有鼠标一条路：单击。于是用 `空格` 切到整屏候选的
人，**还得再碰一下鼠标**才截得下去 —— 一个号称"不需要先选模式"的选择器，
把只用键盘的用户挡在门外。现在 `⏎`（主键盘 36 / 小键盘 76 两个码）采用当前候选，
方向键一像素平移，`⇧ + 方向` 改那一侧边界的大小，`⌥ + 方向` 一步 10 像素。
`Esc` 和 `空格` 原样保留，没被挤掉。

单击和 ⏎ 共用同一段判断（`outcome`），差别只该有一条，而它就是一条规则：
**方向键改过哪怕一个像素，那块矩形就不再是"那个候选"**，⏎ 交出的是这一块区域。
抽成 `adoptAs(_:nudged:)` 之后，"按哪种截"第一次变成了一张能整个跑一遍的表。

顺手修掉一条自己写出来的错：贴到屏边再往外按方向键，矩形一个像素没动，
而 `nudged` 是**无条件**翻的 —— 按错一下键，⏎ 就从「截整屏」变成「截这一块」。
现在只有 `next != rect` 才翻转：空按接住键（不能漏给系统去触发别的动作），
但不改口。没候选时方向键和 ⏎ 都返回 false 交回系统 —— 接住却不做事，
是键被吞了而屏幕上什么都没发生，比不接更糟。

角标跟着说真话：手动挪过之后副标题变成「W × H / ⏎ 截取这一块 · 方向键继续微调」，
提示条和读屏名字都补上 ⏎ 与方向键（学不到的功能等于没有）。

自检这轮挖出两个自己的坑：

**① 有一格在离屏永远测不到。** 真的 `SCWindow` 在离屏进程里构造不出来
（探针实测 `argument passed to call that takes no arguments`，它没有可用的构造器），
而"窗口候选被挪过之后必须降级成区域"恰恰是最容易写错的那一格。所以把判断从
`SCWindow` 身上剥下来，只吃 `Candidate`（窗口 / 整屏 / 区域）和 `nudged` 两个轴，
3×2 全表进 `--logic-selftest`；离屏那份只查它查得动的（接不住不吞键、
空按不改口、翻转之后尺寸跟着走）。

**② 判据会因夹具缺东西而恒红。** "交出的是区域"那条一开始无论如何都 ✗：
`view.window` 是 nil，而"视图坐标 → 屏幕坐标"要问窗口，于是那条路给 nil，
截图语义整个测不到。补一个**从不 orderFront** 的窗口当夹具之后才走通，
无头清点仍然报"跑完没有任何窗口在屏上"。红行不一定是产品的错，
也可能是在说"你这条测试路没铺完" —— 得先分清，才谈得上改。

反向对照两处一起改坏（`nudged` 恢复成无条件翻转 + `adoptAs` 忽略 `nudged`）：
`--logic-selftest` 红 1 条、`--ui-render` 红 3 行，两个门退出码都变 1，之后原样恢复。

### 结论那行不再手抄：38 个组和一句"全部正确"对不上，而对不上的照样打 ✓

`--logic-selftest` 结尾那句「结论：坐标换算、裁剪、…全部正确 ✓」是**手抄的清单**。
它和本仓库反复在治的毛病一模一样：同一个事实写两遍，然后其中一遍先烂掉。
实测就是证据——上面印了 38 个 `── 分组` 标题，结论那句按名字能对上号的只有 18 组：
其余 20 组要么用了另一套词（「屏幕坐标 → 像素坐标」那组写成「坐标换算」、
「浮层层级顺序」写成「层级顺序」），要么**整组不见了**
（「编辑面板初始尺寸」「设置窗的高度分配」「图例的键名加粗」「运行状态行的分色」）。
而它们下面的检查全绿、结论照样打 ✓。一个会漏掉自己内容的摘要，比没有摘要更危险。

改成从走过来的分组标题现读：每个 `print("── …")` 走同一个 `noteGroup`，
它既打印也登记；结尾那句结论从登记表里长出来，并当场校验三件事——
登记非空、每项摘出来的短名非空、短名**互不重名**（重名就说明有两个组在结论里
挤成了同一个词，那等于悄悄少了一组）。摘短名的规矩也配了对照：
摘掉「── 」和括号里那段解释、括号外的尾巴留着（「系统打开 + 最近截图清账」）、
冒号起头的只留冒号前那截（「模板：没看懂的占位符要说出来…」→「模板」，
结论是索引不是把标题再念一遍）、没有括号的标题一个字不改。

反向对照：把 `noteGroup` 改成"38 个组全登记成同一个名字"，那行立刻 ✗、
退出码 1（证明判据不是恒绿）；改回来之后结论行第一次把 38 组一个不落念全。

这不影响产品行为，但它是"自己检查"这条路的底座：**摘要必须是推导出来的，
否则它统计的是抄写员的记性。**`--logic-selftest` 从 290 涨到 295。

### 方向键"按了没反应"：不是键映射错了，是鼠标把选区抢了回去

用户报"方向键微调用不了"，而离屏判据全绿 —— 这组合通常意味着断点在**没被测到的那一环**。
查下来三件事，一件比一件隐蔽：

**① 判据测的是判断，不是投递。** 之前那组键盘判据全都直接调 `applyKeyForSelfTest`，
跳过了「窗口 → firstResponder → `keyDown`」这一段。补了 `deliverKeyForSelfTest`：
装一个真的 `OverlayWindow`（挪到屏幕外，无头那条只查屏内），合成一次真的
`NSEvent.keyEvent` 从 `window.sendEvent` 打进去。结果是键**能**落到视图、选区**能**动一格
（✓），但 `isKeyWindow=false` —— 无头进程是 `.prohibited`，系统不会把 key 给它。
所以"真机上这个窗口成不成得了 key"这一环只能标成 `△`（未验到从 3 条变 4 条），
不能假绿，也不能假红。Esc 走的是 `OverlayWindow.cancelOperation`，是响应链的另一条路，
所以"Esc 能用"根本带不出"方向键能用"。

**② 真正的根因：鼠标一动就把你调好的选区抢回去。** `refreshHover` 原来无条件
`nudged = false` 再按指针重算候选 —— 你用方向键挪了一格，触控板抖一毫米，
矩形立刻吸回"那个窗口"，看起来就是白按。反向对照把这条撤掉再跑，数字很难看：
`{{207,200},{400,300}}` 一抖变成 `{{0,0},{1440,900}}`（连候选本身都换了）。
现在改成**调过之后选区归键盘管**：鼠标移动不再抢回，要换候选就按 `空格` 切整屏、
`Esc` 重来，或者按下鼠标改拖。

**③ 挪不动的时候得说话。** 整屏候选本来就铺满这块屏，方向键一格也挪不了；
以前它静默吞掉这次按键。现在角标会说「已经贴到这块屏的边了 · 换个方向，或指住一个窗口再调」，
`nudgeDidNothing` 这个状态位和这句话一起进判据 —— 只测状态位不算数，得能查出屏幕上真说了话。

顺带把拖拽那组提示改成**「按住 ⇧ 正方形 · 按住 ⌥ 从中心 · 方向键微调」**：
这两个是持续键，拖着的时候得一直压着，光写个符号看着像切换开关。

`--ui-render` 键盘那一组从 9 行涨到 13 行（含两条新的反向对照），
红 0、未验到 4。装机版自验同过，`dist/Grabi-1.0.0.dmg|zip` 已按这版重打。

### 方向键微调整轨删除：修不动的根因，就不要留半套

上一条查清了断点在哪（`refreshHover` 在每次鼠标移动里把 `nudged` 归零再重算候选），
给了两条修法：让键盘那一轨赢过指针，或者拖动后不再响应指针。**两条都没做**——
因为它们都要覆盖层同时记住"用户要什么"和"鼠标在哪"，而这两件事在这一次交互里
天然打架：手指按着方向键、手掌还压在触控板上，指针每 60 Hz 动一次。

删掉之后剩下的那一轨是自洽的：**要精确就走拖动**（`⇧` 锁正方形、`⌥` 从中心，
持续键，松手前不会失效），**要快就单击或 ⏎**（截"那个窗口"）。中间那一档
"用键盘挪一像素"本来就不属于截图工具的核心路径——它服务的是像素级对齐，
而那种活该交给编辑器。

一起删掉的有：`arrowCodes`、`step(modifiers:)`、`nudge(_:dx:dy:)`、`nudge(_:dw:dh:)`、
`adjust`、`nudged`、`nudgeDidNothing`、`Candidate`、`adoptAs(_:nudged:)`、
`blockedNudgeText`，以及 `outcome()` 里那条"挪过就降级成区域"的分支。
`OverlayKey` 从七个 case 缩到四个（`adopt` / `cancel` / `fullscreen` / `other`），
`key(forKeyCode:)` 不再看修饰键——一个键一个意思，修饰键那一层整个退场。

判据没有留旧世界的绿。`--logic-selftest` 键盘那一组从 16 行缩到 9 行，
其中两条是新的反向对照：**四个方向码（123/124/125/126）现在必须全是 `.other`**
（删不干净、留了半套就会红），**两处提示文案都不许再提"方向键"**
（代码删了、文案还写着 = 教用户按一个不存在的键）。
拖拽几何那几条（`⇧` 正方形、`⌥` 从中心）一个字没动——它们本来就是另一套东西。

反向对照实测：把 `if code >= 123 && code <= 126 { return .fullscreen }` 塞回去、
再把"方向键微调"追加进 `dragHintText`，那两条各自变红、其余 7 条保持绿；
还原后红 0。`--ui-render` 红 0、未验到 4，`overlay-drag.png` 角标第三行确认只剩两条。


### 默认改成只进剪贴板，「保留」才写出文件（W2）

需求一句话：截图默认进剪贴板，只有选了「保留」才保存成文件。做起来才发现它的难点
不在"少写一次盘"，而在**预览面板从此是唯一的落盘入口**——于是「截图后显示就地预览」
这个偏好不再只是"少一块界面"，它变成了改变数据去向的开关。这一格最容易写错，而且
错了以后屏幕上一点动静都没有，所以 `ShotCoordinator.savesImmediately(silent:showResultPanel:)`
被单独抽成一张四格的表，交给 `--logic-selftest` 整张跑：

| 静默 | 面板开着 | 立刻落盘 |
|---|---|---|
| 否 | 是 | **否**（只在剪贴板） |
| 否 | 否 | 是 |
| 是 | 是 | 是 |
| 是 | 否 | 是 |

顺手定下来的三件事：

- **「保留」不关面板。** 第一版是"写完就关"，写完才反应过来：那三项文件出口
  （打开 / 在访达中显示 / 复制文件路径）本来就挂在预览的右键菜单上，而它们存在的
  理由正是"工具栏做极简之后总得有个落脚点"。一按就关 = 那三项在这块面板上永远不会
  亮起来。现在按完「保留」，那颗按钮变「已保留」并禁用（再按一次会在同一秒写出第二个
  同名文件），面板留着，关掉它走 Esc 或点别处。
- **「丢弃」从此有两义。** 没保留过，它删的是剪贴板里那一份，磁盘上根本没动过；
  已经保留过，它删的是磁盘上那一份，走废纸篓。tooltip 和右键菜单的标题都按状态现取
  （`keepDiscardTitles(saved:)` / `contextMenuItems(isOCRMode:saved:)`），写成一句
  就有一半是假的——而用户正是按那一句决定点不点的。
- **剪贴板那个开关删了。** 它原来的意思是"落盘之外顺带也复制一份"；现在复制就是
  主去处，留着它等于留一条"截图截到空处"的可达配置（既不落盘也不进剪贴板），
  而那种状态得额外编一句警告才圆得回来。真不想要剪贴板里那份，「丢弃」就在手边。

`.txt` 旁车跟着挪了位置：从"识别完就写"改成"保留时一起写"，因为"同名"得先有个名。
中间那段不能装成已办——这个开关历史上真当过一次空壳（勾了、什么也没写、也不吭声），
所以图没落盘时那句改成明说的预告（`ImageWriter.ocrTextPendingStatus`），
并且 `writeSidecarIfNeeded` 拿临时目录真跑了两个开关状态，勾与不勾各钉一头。

判据：`--logic-selftest` 38 → 39 组，新那组 15 行。反向对照分两次跑——
四处一起改坏（`savesImmediately` 恒真、`keepDiscardTitles` 两种状态同一个词、
预告那句写成「已存」、设置里那行不再引用开关真名）红 6 行；单独把
`!showResultPanel` 拆掉，恰好「普通截图 + 面板关掉」那一格红。
`--ui-render` 出图 52 → 62 张：工具栏五种形态各画两遍（`toolbar-*-kept.png`），
「已保留」那颗禁用按钮得真画出来才看得见，顺带也验了它确实被排除在对比度判定之外。

还修掉一处自己造的脏：`--ui-preview` 以前为了迁就 `show(url:)` 的签名，会先往用户的
截图目录写一张演示图、拍完屏再挪进废纸篓。现在签名里没有 url 了，那张图也就不必存在。


### 截图框改成「细线 + 四角括号」，八颗假把手撤掉（W3）

覆盖层的选区框原来是：3pt 黑晕 + 2.5pt 蓝线，拖拽时再在四边中点和四角画 8 颗白点。
那 8 颗点是**假把手**——覆盖层根本没有手柄拖拽，`mouseDown` 一律"从这个点重新开始画一块"，
所以按在一颗白点上得到的不是"拖动那条边"，而是一块新选区。画了个能抓的样子、
按下去不抓，正是这个仓库一路在抓的那类东西。

改完的样子：

| 位置 | 现在 | 为什么 |
|---|---|---|
| 覆盖层选区 | 1pt（拖拽时 1.5pt）强调色细线 + 四角白色括号 | 细线说"边界精确到这一像素"，括号说"这四角定义了这一块"；两者都不暗示能抓 |
| 预览面板那一圈 | 四角方块、四边中点躺在该边上的短棒 | 八个都是活的，而它们之间唯一的区别就是"改一条边还是两条边"——以前八个圆点，这个区别只在形状上丢掉了 |

括号臂长不是定值：`cornerTick(minSide:)` 取短边的两成、上限 30，并且**一条边上两只不许碰头**
（至少留 4pt 缝）。不夹后半句的话，一块 24×18 的小选区会被四对括号连成一整条实线，
那又变回"框"了；小到连 8pt 都放不下就干脆不画，细线还在。

判据这一节新写在一个函数里（`--ui-render` 的「选区框与手柄形状」，8 行），关键是
**把框单独画到一张透明底位图上再量**。真那一张压在桌面合成图上，而那块桌面左半是
纯白的窗口——"框上有没有画白点"这种问题在混了背景的图里问不出答案：白的地方白点
量不到，灰的地方又像有白点。透明底之后白色只剩"框自己"一个来源，于是一句
"白色像素一个都不许落在四角之外"同时钉住两件事：那 8 颗点没回来、四角括号真画了。

其余几条：臂长政策扫 7 个边长（含 16 和 1440 两头）；`cornerTicks` 恰好四段 L、
每段两臂各 30；按在旧版那颗白点的位置上，回报的是 `{{300,400},{20,0}}`——
以按下点为一个角的新矩形，不是被推走的那条边；预览手柄按形状分两组断言。

反向对照四处一起改坏（把四颗中点白点画回去 + 括号那段直接 return + 臂长对大矩形返回 0
+ 八个手柄全画成方块）：越界白点 128 个 ✗、四角像素 0/0/0/0 ✗、四边短棒 ✗，退出码 1。
还原后红 0。装机版自验同过。

一处顺带的口径修正：README 的操作表以前写着"拖动时四角出现调整手柄"——那是那句谎话
印在说明书上。现在改成"要调边界是松手之后在预览面板上拖手柄"，那是唯一真的地方。



### 工具栏重排 + 画笔 / 形状标注（W4）

工具栏从左到右固定成四段：**标注组（画笔 / 形状 / 颜色 / 撤销）‖ 主按钮 ‖ 保留 / 丢弃 ‖ 收起**。
四种形态（normal / ocr / busy / failure）都带着标注组 —— 识别跑到一半想圈一笔、
识别失败想圈一笔说清哪里认错了，都不必先把工具栏切回去。

标注画在**就地预览面板**上（这是先前定下的决定，不是编辑面板）：圈一笔的目的几乎总是
"这张图里这一块我要留着说"，那一下应该发生在图还在眼前的时候。

真正麻烦的是"画在屏幕上的那一笔必须就是存进文件的那一笔"：

- 笔迹坐标按选区**归一化**存（0…1）。屏上怎么排布、面板被挪到哪儿、窗口多大都不影响
  这一笔落在图的哪个相对位置。
- 线宽屏上定 3pt，落盘按图片像素尺度反算。1440×900 的屏 2x，屏上 3pt 在文件里就是 6px。
  这条链在 `--logic-selftest` 里从"屏上一点"一路走到"文件里第几像素"，
  中间不换尺子（换一把尺子就是造一份新的真相）。
- 形状按钮的图标**永远显示点下去会发生什么**：没在形状工具上时显示"下一个要用的"那种，
  而不是当前那一种的灰版 —— 图标说"矩形"、点下去画椭圆，就是图标在撒谎。
- 「撤销」没有可撤的东西时是**灰的**。这一排里只有它的状态取决于历史，
  而"按下去叮一声、什么也没发生"是这一轮反复在修的那一类毛病。

自检添了两处：`--logic-selftest` 的「标注」9 行（形状轮转、归一化往返、
箭头倒钩角度、撤销栈、线宽反算），`--ui-render` 的「标注合成」6 行 ——
后者是真的把笔迹合成进一张位图，数"文件里那条线有几像素宽"，
不是检查"代码里调了 draw 没有"。

### 状态栏菜单 16 → 8、设置页 34 → 24、图标重画（W5）

菜单那 8 行和每行的去向我写在上面「菜单栏」那一节了。这里记三件**只有做的时候才发现**的事。

**一、`prefix(2)` + `suffix(2)` 把一栏说明印了两遍，而所有断言照样绿。**
设置页「截图时的操作」那栏原本四条、各占一行，我把它折成两组：
`captureHelpTexts.prefix(2)` 和 `.suffix(2)`。实际那个数组**只有三条** ——
于是中间那条（「截完之后：」整栏 6 行）在窗上印了两遍。

现有那两条检查都抓不到：一条问"这栏在不在窗上"（在，而且两遍），
一条数"面板有几行"（两栏还是两栏）。是我去看 `settings-hotkey.png` 时看见的 ——
这一轮"渲染出来给人看"又一次证明自己不是仪式。

修完之后加了一条**数次数**的断言，不数"在不在"：

```
      ✓ 每一栏在窗上正好出现一次（次数 1/1/1/1）　·　重叠的 prefix/suffix 会让中间那栏印两遍
```

**二、行数这把尺子要能防"糊弄它"。** 设置页从 34 行压到 24 行，靠的是两种真折叠：
`legend(...)` 把多行说明排成一个紧凑栈（组内 3pt），`grouped(...)` 把一条说明和
**它管的那个控件**钉成一组。横向并排的三个语言勾选框算一行，一组也算一行 ——
数出来的是眼睛扫到的行数。把两行文字硬塞进一个标签（字号间距都不动）不会让数字变小，
所以这个数字不是可以拿排版糊弄的。每个面板各封一个上限（6 / 7 / 7 / 8），
超了会红得说明白是哪一格。

**三、`minSize` 从内容算，但"内容要多宽"这件事在临界 1pt 上不连续。**
上一节那条"从面板自己的 fittingSize 算最小宽"这次自己翻车了：设置页一改排版，
`能拖到的最窄宽 556　面板最宽需要 542 + 32 = 574` 就红了。查下去不是算错，
是**量的时机**：会折行的说明标签要多少取决于你给它多少 —— 摊到 1200 宽它按自己一行排完
（报 523），压到 524 它就照 `preferredMaxLayoutWidth` 折行、改口要 542。
差的那 1pt 让一条说明从"折两行"翻成"再挤一行"，映射在这点上跳了 19pt。

迭代这个映射收在哪一格取决于起点，所以不迭代了：窗口下限直接压到
**"谁都不必额外折行"那一格**（= 最大的那个 `preferredMaxLayoutWidth` + 卡片内边距 + 留白），
再和控件固有宽取大。卡片内边距从**真卡片**的 `edgeInsets` 读，不抄 `section()` 里那份。
现在读到 596，而面板在最窄那一档要 574 —— 余量 22pt，抖不抖都与结果无关。

**图标**换成自己画的一副四角括号（和覆盖层那副同源），三份状态只换中心那点东西。
`--ui-render` 添了 11 行像素断言：常态有笔画、**常态中心必须是空的**（这条同时是
另两档的反证）、闪一下时括号一动不动只有中心多了东西、四角按象限配重一样
（75/75/75/75）、三份都是模板图、三份朗读名各不相同，最后一条是**空图反证**：
一张什么都不画的同尺寸位图必须读到 0 个像素，否则上面那些数是把底色数进去了。

### 视觉常量收成一份（U1）

用户说的"不统一"，落到代码里是具体的数字差：角标内边距一份 9×6 一份 9×5、
HUD 底板一份黑 0.92 一份 0.82、圆角六种、字号 11 和 12 各出现十几次、
截图遮罩 0.32 而预览压暗 0.45（于是松手那一下屏幕会自己再暗一档，像换了个 app）。

`Support/Design.swift` 收的是**跨面共用**的那部分：四档圆角、三档 HUD 文字亮度、
七种字号、一根 1.5pt 细线、四档间距、两段时长，以及遮罩 / 压暗 / 角标底那几层。
两档压暗（0.32 / 0.45）**故意没合并** —— 截图进行中要隔着它判断内容，
截完之后是要让用户专心看那一块，这是设计而不是漂移，所以各有一个名字
（`dimSelect` / `dimFocus`）。某一界面独有的尺寸（工具栏高 42、缩略图 54×40）
留在原地：把它们也搬进来，这个文件就会变成没人敢改的杂物间。

角标那块黑底 + 一到三行字以前是两份几乎一样的代码，现在是一个 `HUDBadge.draw`。
统一这件事**不能靠"两边都引用了同一个常量"来宣布完成** —— 引用了同一个常量，
中间任何一步加了系数、夹了边界、按外观解了个色，屏幕上就是不统一。
所以 `--ui-render` 里那组「统一化对账」量的是**合成之后的像素**：
工具栏那条底板和结果角标那条底板，逐通道比灰度必须一样；
角标在深色 / 浅色两趟里解出来的颜色必须相同。

### 标注第二轮：第一下是选中，以及"没有一张图真的画过一笔"

用户看完上一轮的工具栏说了四件事：形状第一下点的是"换下一种"而不是"开始画"、
来回点着切不方便、颜色那颗要点六下才绕回来、画笔时鼠标还是那只箭头。
前三条改成了**四种形状各一颗 + 颜色点开一栏（六档候选色 / 三档线宽 / 系统调色盘）**，
第四条换成一枚笔尖环。剩下那句"你自己再想想还能怎么改进"翻出来五件事，
其中三件是改的时候才发现上一轮留下的洞：

- **选中态改成"加一块常亮的底"，不是"把图标放大一档"。** 本来打算沿用 `prominent`
  那条路（放大 + 强调色），试完发现它顺带改了那颗的宽度 —— 整排跟着重排，
  用户刚点完，旁边几颗就从鼠标底下了。标注是"点一颗、拖一笔、再点下一颗"的活，
  每选一次布局抖一下比看不出选中更烦。现在强调色留着，底换成单独一层 `CALayer`，
  三种状态（没历史 / 有历史 / 选中）量出来都是 960px 宽。
- **`Esc` 和点面板外以前会把画了一半的笔直接吞掉。** 面板上明明圈着红框，
  剪贴板里却是干净的那张 —— 而那句话（"图留在剪贴板里"）是写在设置页上的。
  现在两段：正画着先停笔，再按一次才收面板；收之前把带标注的那张刷回两个去处。
- **「清空」这一档整个不存在**，只能一笔一笔撤。一笔一笔撤到第十笔不是"撤销"，是体力活。
  加了一颗按钮，并且让撤销在清空之后**把整批还回来**（`lastCleared`），
  否则"清空"就成了这个产品里唯一一处不可逆的删除。
- **三处 `copyImageToPasteboard` 里有一处不看返回值**，无条件弹一句「已复制图片」。
  编译器把另外两处标成了 unused-result 警告，那一处恰好是自己吞掉的 ——
  警告只抓到"没接"，抓不到"接了但没判"。现在三处都回读剪贴板再报，
  成功那句带尺寸（"复制的是刚圈过这一张"只有数字能证明），失败那句给下一步。
  ⌘C 和工具栏那颗也并成同一条路，不再一个说话一个沉默。

**但这一轮真正的收获是自检自己的两个洞。**

一、`--ui-render` 里关于标注的判据，**一条都没画过笔**。读的全是字符串：
tooltip 写了什么、菜单有几条、tag 对不对、按钮有几颗。字符串全对，
而"五种工具在图上长什么样"这张图从来没存在过。于是补了一节：

```
── 标注画出来是什么样（图上落墨 / 选中态 / 笔尖光标）
      ✓ 五种工具在图上各留了一块墨（每种 ≥40 px）
      ✓ 反向对照：底图里这三档颜色本来一块都没有
      ✓ 画完一笔之后「撤销 / 清空」自己亮了（差 549 个像素，全在那两颗的格子里）
      ✓ 点中之后那颗自己画出了选中底（差 488 个像素）　·　不是只有 tooltip 换了词
      ✓ 三种状态这一排一样宽（读到 960 / 960 / 960 px）　·　按钮不许从鼠标底下溜走
      ✓ 五种形态最宽的一排 648pt　·　上限 660pt　读到 normal=463 ocr=648 busy=412 collapsed=16 failure=545
      ✓ 反向对照：多塞两颗按钮就 692pt，撞破上限（这条不是永远绿着的装饰）
```

那条"全在那两颗的格子里"是 `pixelDiff(inside:)` 第一次被用在工具栏上：
差集必须整个落在「撤销 / 清空」两格的矩形里，只数"有没有差"的话，
整排都在抖也算通过。

二、`let shapeCursorOK = layer.cursorForSelfTest === NSCursor.crosshair` ——
这个值**从来没进过任何一条判据**。那句打印写的是
「画笔是自定义的笔尖光标，形状是十字」，读的人以为两条都查了，实际只查了前半句。
是编译器的 unused-variable 警告抓到的。现在拆成两条各查各的，
再加一条反向对照（笔尖和十字必须是两只光标，否则那两句一起变成谎话）。


## 性能

M1 MacBook Air，1440×900 逻辑屏（2880×1800 物理像素），release 构建：

| 指标 | 数值 |
|---|---|
| 常驻内存（phys_footprint） | **27 MB** |
| 截图耗时 | 270–430 ms |
| 写盘（PNG 1.1 MB） | 40–85 ms |
| OCR（缓存后） | 200–700 ms |

几个刻意的取舍：

- **不用 SwiftUI**。设置面板纯 AppKit 手写，省掉 SwiftUI 运行时那几十 MB。
- **报错不响系统提示音**。`NSSound.beep()` 只说"不行"，不说"怎么办"，而且是这一排
  交互里最刺耳的一种反馈。现在全部走能写字的通道：工具栏失败条（**带着「再试一次 /
  保留 / 丢弃」一起出现**，否则等于让用户去点一个已经不存在的按钮）、结果角标、
  编辑面板的状态行。快捷键框收到不合规的组合时也只是把框里的字换成
  「至少加一个修饰键」/「再加一个修饰键（如 ⌃⌥）」并继续录制，不用重新点一次。
- **所有过渡都过 `Motion.duration()`**：系统「减弱动态效果」开着时压成 0，
  状态变化照常发生、只是没有动画。收在一个入口里，比每个调用点各写一次 if 靠谱。

- **截图前先撤覆盖层，等 120 ms 再抓图**，否则框选遮罩会残留在截图里。
- **区域截图先整屏抓取再本地裁剪**，而不是用 `SCStreamConfiguration.sourceRect`——后者坐标系在各版本上语义不一致（点 / 像素），整屏抓 + 裁在任何缩放组合下都稳定。
- **OCR 启动预热**。Vision 第一次加载中文语言包要几十秒（之后走系统缓存只要 ~200 ms），这个代价不能落在用户第一次截图上，所以启动后 0.4 秒就在后台静默跑掉。

## 已知限制

- 最低 macOS 14（截图依赖 ScreenCaptureKit）
- 自启动走 `SMAppService` 需要 macOS 13+；更早的系统退回手写 LaunchAgent
- 首次注册后台项后，系统可能要求你在「系统设置 › 通用 › 登录项与扩展」里确认一次
- 区域截图不支持跨显示器拼接（选区收敛在起始屏幕内）
- 用 Apple Development 证书签名的 app 只能本机运行；分发给别人需要 Developer ID 签名 + 公证
